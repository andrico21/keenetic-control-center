# MCP tools

Generated by `cargo xtask gen-tool-docs` from the `kcc-mcp` tool registry; do not edit.

Every router-targeting tool takes `host` (a router profile id). Handlers re-check the
exact operation permission and router scope; the permission column is the coarse gate
the RBAC layer applies to the tool. Destructive operations need `confirm: true` and
`[mcp] allow_destructive = true`; a refusal says which one is missing with the error
code `destructive_disabled` or `confirm_required` (also used when a management,
migration, or preset change lacks `confirm: true`). A write the router accepts but
does not apply fails with
`verification_failed` and the `field` that read back unchanged; `validation_failed`
means the input was refused before anything was sent. No tool saves implicitly.

Every mutating raw tool, including `kcc_cli_parse`, requires confirmation and the server
switch for management or destructive requests, and the `Destructive` role permission for
destructive ones. The recovery timer kcc arms around a management change is authorized
by the change's own permission; the server switch stays required for raw management
changes even when the role holds `Destructive`.
Negative `no` commands are destructive. Management nodes retain their recovery timer
even when a destructive sibling raises the maximum request risk.

`kcc_migration_apply` and `kcc_preset_apply` need `Read`, `Migrate`, `Write` and `Save`
and arm the recovery timer under `Migrate`. A `rollback` with `kcc_migration_finish`
also needs the `Destructive` role permission (otherwise `forbidden`, with nothing sent)
and the server switch.

A management change on a router whose recovery mechanism cannot be determined (it
reports neither a system mode kcc knows nor a fail-safe timer) fails with
`router_mode_unknown` before anything is sent.

After recovery arms, unsuccessful cleanup returns `management_applied_fail_safe_armed`
when at least one change item succeeded, or `management_outcome_unknown_fail_safe_armed`
when every change was refused, work failed, or its outcome is unknown. Successful reads
do not count as applied changes. Batch recovery errors retain `responses`, including
the refused `ok: false` items; partial application refers only to successful changes.
When the arm is refused and so is its disarm, the code is
`management_not_sent_fail_safe_armed`: nothing else was sent, but the timer may be armed.
When the configuration was saved but the disarm failed, the code is
`management_saved_fail_safe_armed`: the router may restart with its saved configuration,
which includes the change.
These codes carry a localized English `message` explaining recovery;
the timer remains armed and will restore the saved configuration, discarding unsaved changes.
A locally refused migration commit returns `management_not_committed_fail_safe_armed`:
nothing was sent, the timer remains armed, and the migration is retained for retry.
A migration rollback the router accepted before it stopped answering returns
`migration_rollback_restarting`: the router is restarting with its saved configuration
and the migration is closed, so a retry cannot reboot it again.
Successful cleanup preserves the original work error; when the arm itself was refused
and its disarm accepted, that error also carries a `message` saying nothing was applied
and the timer is off. Failed-change audit parameters
include `fail_safe_armed: true` when recovery remains armed.
