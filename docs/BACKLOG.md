# Backlog

Open items that do not block a release. One line each: where it is (`file:line`) and why
it stays open. Line numbers are those of the tree at the time of writing.

## Not proven on hardware

No live suite has run against a real router yet: every `live_*` test logs `live-skip` and
returns, and `docs/FIRMWARE.md:10` still says "live verification not yet run" for 5.1 (the
firmware doc test accepts that text). Until a test router is available, these behaviors
rest on the manuals and the fake router only:

- The Windows path for sealed credentials and key files (owner-only ACLs, `crates/kcc-app/src/persist.rs:559-608`) has only been built, not run, on Windows. The macOS, Windows and aarch64 CI legs are likewise unproven.
- Whether a real router answers 404 to `GET /rci/system/reboot`, and whether the scheduled-reboot fallback (extender, access-point and repeater modes) and the native fail-safe timer behave as the manual describes (`spikes/live-router/RESULT.md:21-23`, probes 7, 7b and 8, are marked NOT-RUN).
- Whether a real router executes a space-joined root key such as `{"system reboot":{}}`, and whether it accepts an empty object at a namespace (the raw request rules in `docs/SECURITY.md` are written to be safe either way).
- Whether the members of a real LAN bridge are `include` or `inherit` lines, and whether a real `show interface` answer is keyed by interface id (`crates/kcc-migrate/src/rules.rs`).
- Whether a real router refuses an `include` of an unknown member, accepts WireGuard leaves on a bridge, or deletes `Bridge0` (`crates/kcc-domain/src/interfaces/guard.rs`).
- The shape of a real `show running-config` answer (`crates/kcc-domain/src/firewall/read.rs:45-60` reads it as text) and whether the router accepts every abbreviation the catalog allows.
- `crates/kcc-migrate/src/interface_names.rs:4` decides whether an interface name is physical or logical with a name-shape heuristic taken from the documentation. The unit test pins the documented shapes only.
- The default `[outbound] argon2_max_iterations = 16` (`crates/kcc-app/src/settings.rs`) is not verified on a real KeeneticOS 5.2 router. If a real router asks for more than 16 Argon2 iterations at ndw4 sign-in, sign-in fails with "router authentication cost exceeds local policy" until the operator raises the setting.
- `crates/kcc-domain/src/configuration.rs:112-117`: the recovery mode for a router that reports no system mode assumes that 4.3 and 5.0 report a boolean `fail-safe.active` in `show last-change`. This is from the documentation. If it is wrong, kcc refuses the change with `router_mode_unknown`, which is the safe direction.

## Upstream (rmcp-server-kit)

- `crates/kcc/src/server.rs:139` builds the server configuration without `max_concurrent_requests`, and the kit logs that it is unset. A bound would cap held requests besides the per-router lease. The setting is the kit's to expose or default.
- The kit's HTTP listener has no header read timeout, so a connection that sends a request line and then goes silent stays open for more than 70 seconds. It cannot be set from `crates/kcc/src/server.rs:139`.
- The kit logs a transport-level 403 (an MCP request refused before any tool runs) itself; it is not written to `audit.jsonl` (`crates/kcc-mcp/src/support/audit.rs:11` audits tool-level refusals only).
- The kit inserts `Cache-Control` on every response or on none, so kcc turns it off to keep the immutable policy of hash-addressed assets (`crates/kcc-web/src/csp.rs`), and the kit's own routes (`/mcp`, health, version) go without it. A mode that sets the header only when the route has not set one would let kcc keep `no-store` on those routes (project overlay deviation 5).
- `docs/rust-guidelines/UPSTREAM.md` lists the guideline changes the owner still has to propose by hand.

## Known gaps

- `crates/kcc/src/server.rs:203-206`: on SIGTERM with nothing in flight, `kcc serve` exited about 4.4 s after it logged "jobs drained". Traced to the router log collectors: their waits between reads (the 5 s stream interval, the 30 s poll interval) could not be cancelled, and the collectors were stopped one after another, so the delay grew with the number of routers. The waits now end on cancellation and all collectors stop together (`crates/kcc-telemetry/src/logs/service.rs`, `runtime.rs`). Not re-measured on a `kcc serve` process; if a delay remains with `[logs]` disabled, its cause is elsewhere.
- The CLI has no SIGINT or SIGTERM handling during a safety bracket (`crates/kcc/src/cli/change.rs:228`). If the process is killed, the router's own timer restores the saved configuration; `kcc serve` and `kcc mcp stdio` do wait for their brackets.
- The Web standalone rollback is not mode-aware (`crates/kcc-web/src/config_page/safety.rs:121,170-188`): on a router in scheduled-reboot mode it refuses ("not armed") instead of rebooting like the CLI does.
- `crates/kcc-web/src/page_kit/facts.rs:14`: the Web facts cache holds a router's catalog for 600 s, so a firmware change is noticed up to ten minutes late.
- `crates/kcc-web/src/dns_vpn/dns_checks.rs:82` builds its change with a fixed `Risk::Write`; it is the only Web page that does not take its risk from the domain planner.
- A 403 pre-check was dropped from two Web paths that now run through the shared submit step (`crates/kcc-web/src/dns_vpn/vpn_import.rs:76` and the VPN dialog in `vpn_forms.rs`): a role with `Write` but not the planned risk's permission sees the kit's forbidden outcome instead of the 403 page, and reboot, reset and mesh-restart ask for confirmation only after the context is read.
- The wizard finish routes still have three entry handlers for the migration (`/commit`, `/rollback`, `/{way}` in `crates/kcc-web/src/migrate_wizard/routes.rs:52-57`) and one for presets (`/{way}`, `presets_page/routes.rs:82-84`). Making them one changes edge behavior (the content type of commit, the order of dialogs, the order of the unknown-way 404), so it needs a decision.
- The firewall page reads rules as running-config text (`crates/kcc-domain/src/firewall/read.rs`, `firewall`), while the CLI, MCP and the planner's read-back use `configured_list` (`show rc` JSON, IPv4 only, the targeted list alone; a rule in another form is kept as `ListedRule::Unstructured`). Two readers of the same data remain; unifying them would change the CLI's request count.
- Firewall rule read-back is a presence check (`crates/kcc-domain/src/firewall/change/verify.rs`): when the target state already holds before the write, it cannot tell an applied write from an ignored one. Adding a rule equal to one already in the list passes even if the router ignored the line, and removing one of two equal rules fails on the remaining copy. Counting equal rules before and after would close it; the VPN client secret read-back has the same limit (left with the VPN client work).
- `crates/kcc-domain/src/firewall/lists.rs:197-198` skips an interface binding whose direction is not `in` or `out`. The firmware only writes those two.
- The master key (`crates/kcc-app/src/secrets.rs:336`) is the plaintext root of trust: anyone who can read that file can open the state store. Podman's default file secret driver also keeps the deployed secrets unencrypted on the host (`deploy/podman/README.md:51`). Wrapping the key with `systemd-creds` or a TPM is a possible future step.
- `ApplyNeeds::raw_restore` (`crates/kcc-domain/src/configuration/apply_needs.rs:13,31`), the flag that adds `Destructive` for a raw restore, has no production caller yet; the Web raw restore holds `Destructive` through its own constant.
- One CLI refusal has no machine-readable handle: an absent firewall rule property prints a sentence with exit code 4 and no code (`crates/kcc/tests/cli_domain_writes/admin.rs:99` pins the exit code only).
- An MCP client that disconnects or cancels in the middle of a management change gets no reply for that call, but the bracket completes: rmcp 3.9 runs each request in its own detached task (`rmcp-3.9.0/src/service.rs:1609`, `tokio::spawn` at `:1332`) and kcc-mcp never reads the request's cancellation token, so nothing cancels the bracket and the disarm and its audit entries still happen (`an_mcp_bracket_outlives_a_disconnected_client` in `crates/kcc/tests/serve_bracket/disconnect.rs`). The kit's `[server] request_timeout` bounds only the time until the SSE reply starts (`rmcp-server-kit-3.21.1/src/transport.rs:2744-2751`), so it never cuts a running call: the reply arrives (`an_mcp_bracket_outlasting_the_request_timeout_answers`). Only a process exit can end the task early, and `kcc serve` and `kcc mcp stdio` wait for open brackets first (`crates/kcc/src/server.rs:203,235`).
- DNS writes other than the HTTPS upstream have no read-back: `crates/kcc-domain/src/dns/change.rs:35-40` builds a `VerificationSpec` for `DnsChange::HttpsUpstream` only, so a name-server, TLS upstream, static host or filter change is reported as applied without reading it back. Fix: add a `show running-config` or `show dns-proxy` read-back for each.
- The migration run re-arms the scheduled reboot by itself with `SafetyNet::arm` outside the shared bracket (`crates/kcc-migrate/src/apply/execute.rs:200`, extender, access-point and repeater modes), as a keep-alive. This predates the bracket seam; `docs/ARCHITECTURE.md` does not mention it.
- The CLI prints the generic authentication headline, `cli-error-auth` ("Authentication failed. Check the login and the password file.", `crates/kcc-i18n/locales/en/cli.ftl:12`), with exit code 3 when it refuses a secret file that group or others can read, even on `router add`, before any router is contacted (reported by the final review). The second line has the correct chmod hint. Fix: a dedicated headline such as "A secret file is readable by other users".
- Wording of Web and CLI answers, reported by the final review and not all re-checked in a browser:
  - `audit-entry-pending` (`crates/kcc-i18n/locales/en/common.ftl:48`) says "Done. The audit log is busy; ..." and drops the "It stays unsaved until you save the configuration." advice of `web-kit-done-unsaved` (`web.ftl:491`) when a management change is answered under a busy audit log.
  - The migration apply dialog, preview and running page (`web.ftl:1452,1484,1501`) say "fail-safe timer" on every router, although kcc arms a scheduled reboot on an extender; only the warning at `web.ftl:1353` says so.
  - `web-presets-applied` (`web.ftl:1863`) tells every role to "roll back", but a role without `Destructive` sees no Rollback button (`web-presets-rollback-forbidden`, `web.ftl:1871`, explains it elsewhere).
  - `cli-confirm-missing` (`crates/kcc-i18n/locales/en/cli.ftl:24`) was seen printing the router as "-" for `kcc --router <id> migrate apply` without `--yes`.
  - The log-sink secret refusal (`crates/kcc-telemetry/src/logs/sink.rs:250`) uses its own sentence, not the shared `errors-secret-file-permissions` (`crates/kcc-i18n/locales/en/errors.ftl:11`) that the TLS key and CLI inputs use.
  - A plan refusal banner reads "Result interface: invalid value." (`web-explorer-issue-value`, `web.ftl:444`) and keeps the English field name inside the Kazakh text.
  - Kazakh dates in wizard and preset reports were seen with the month as "M11"; the formatting code has not been located.
  - Audit entries for an interface going down carry the catalog path `interface up` with the field `no` (`web.interface_down`, `crates/kcc-web/src/net_interface_actions.rs:37`), which reads like the opposite action; a display label would help.
- A direct rollback POST from a role without `Destructive` answers a 403 page whose router selector says "No routers configured" (`web-fleet-empty`, `crates/kcc-i18n/locales/en/web.ftl:30`). The refusal and its audit entry are correct; the page context is not. Reported by the final review, not re-verified.
- At 390 px the section tab strips scroll sideways with no fade or other hint (`crates/kcc-web/assets/css/app.css:1357`, `.tabs__list`, and `:2125`, `.lan-views__list`), and the third tab can be cut in the middle of a glyph.

## Decisions kept on purpose

- The session keepalive was removed. It was code in `crates/kcc-rci/src/session.rs` meant to send a periodic request so an idle router session would not expire, but nothing ever started it. If a long-lived server needs idle sessions kept open, it has to be rebuilt and wired in.
- The Argon2 budget for the ndw4 sign-in math is fixed at one derivation at a time (`crates/kcc-rci/src/ndw4_keys.rs:17`); the setter for it was removed because nothing called it. A fleet that signs in to many routers at once therefore derives their keys one after another.
- Two small helpers were not replaced by crates: the edit-distance function (`crates/kcc-catalog/src/validate.rs:380`, instead of `strsim`) and the router network check (`crates/kcc-rci/src/outbound.rs:44`, instead of `ipnet`). Both are short, tested and need no new dependency.
- Two glob matchers with different semantics exist, and neither is shared: `crates/kcc-migrate/src/rules.rs:767-796` (rule globs: case-sensitive, a segment may end in `*`) and `crates/kcc-migrate/src/presets/glob.rs:4-52` (preset group patterns: case-insensitive, a segment may have a `*` in the middle, plus a catalog-path matcher). Merging them would change what existing rules and presets match.

## Tests

- The golden-page harness does not cover everything. On the KN-1811 fake, created PPPoE and PPTP connections are not listed back, so its `internet/password` and `vpn/credential` submits answer 404. Later steps of the migration wizard and preset runs, SSE streams, raw restore and one-time API keys are not captured. The harness was also reported not to normalize the stylesheet asset hash and its `integrity=` value, so a comment-only edit of `app.css` changes every page snapshot; normalizing them would keep the stylesheet snapshot as the single witness.
- Some tests still wait in real time: `crates/kcc-telemetry/tests/logs.rs:239,257,290,292`, `crates/kcc/tests/metrics_serve/runtime.rs:249` (a 500 ms poll loop), `crates/kcc-web/tests/dashboard.rs:249,251`, `crates/kcc-web/tests/explorer_pages/bracket_ordinary.rs:54`, `bracket_budget.rs:39`, and the finish-recovery tests `preset_finish_recovery.rs:240` and `wizard_finish_recovery.rs:261`. Each should wait on the exact state change or a paused clock.
- Audit receipt and writer paths no test pins: `Pending::is_pending` and `AuditReceipt::is_pending` (`crates/kcc-app/src/audit/receipt.rs:71,157`: a receipt must stop reporting pending once its entry is written), `Pending::wait_until` (`receipt.rs:95`: queued, then written before the deadline, on a paused clock), `AuditLog::flush` (`crates/kcc-app/src/audit.rs:478`: returns 0 once the queue drains and stops waiting on a dead writer), a `verify_chain` fixture with only a sequence gap (`crates/kcc-app/src/audit/chain.rs:60`: tamper `seq` and recompute the hash), the rotation boundary at exactly `rotate_bytes` (`crates/kcc-app/src/audit/state.rs:127`), and the validated body of the arm line in `cli_request` (`crates/kcc-domain/src/configuration.rs:353`: the `no ` guard changes only the body used for catalog validation, so the request sent stays the same).
- `kcc clients wake` against the fake router fails with "RCI request failed"; the fake's limitation has not been looked into.
- `cargo xtask` finds the repository root at compile time (`env!("CARGO_MANIFEST_DIR")`, `xtask/src/main.rs:214`), so when two checkouts share one `CARGO_TARGET_DIR` the second reuses the first's binary and checks the first tree. Fix: resolve the root at run time (`cargo locate-project --workspace` or the current directory). Developer tooling only.
