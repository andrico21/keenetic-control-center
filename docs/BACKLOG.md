# Backlog

Open items that do not block a release. One line each: where it is (`file:line`) and why
it stays open. Line numbers are those of the tree at the time of writing.

## Not proven on hardware

No live suite has run against a real router yet: every `live_*` test logs `live-skip` and
returns, and `docs/FIRMWARE.md:10` still says "live verification not yet run" for 5.1 (the
firmware doc test accepts that text). Until a test router is available, these behaviors
rest on the manuals and the fake router only:

- The command forms the planners and the catalog build from the manuals have never reached a real router. These are the order of `ipv6 route <prefix> <interface> <gateway>` and the `ip route` metric on 4.3, the `system log server` and `wireguard peer endpoint` forms, planning an interface as `interface down`, the `interface <name> vlan-id` line the segments send, the host-name form of `ip http proxy upstream` (typed in the catalog as a host name), the firewall reorder form `access-list <name> rule <index> order <position>`, and `no ip dhcp pool <name> dns-server` (the fake router's rule for it was relaxed to accept the bare leaf).
- A same-value rewrite of a router account, PPP or Wi-Fi secret is reported as "did not change" because the md5 and `ns3` encodings are deterministic and kcc cannot tell it from an ignored write. This follows from the algorithms and the fake router, not from hardware.
- The end-to-end driver (`deploy/podman/e2e.sh`) was proven against the fake router and, in container mode, against a podman image. A real `workflow_call` run of the release workflow, a tag push and the required status checks (set in GitHub) cannot be exercised from a checkout.

- The Windows path for sealed credentials and key files (owner-only ACLs, `crates/kcc-app/src/persist/windows_acl.rs`, checked by `crates/kcc-app/tests/windows_acl.rs`) runs in CI on GitHub's `windows-latest` runner (Windows Server 2025), as does the whole test suite, under a non-elevated token; the macOS leg runs too. Still not verified: a real user's Windows machine (domain-joined accounts, redirected profiles, antivirus, non-NTFS volumes) and a real macOS or Windows deployment of `kcc serve`.
- Whether a real router answers 404 to `GET /rci/system/reboot`, and whether the scheduled-reboot fallback (extender, access-point and repeater modes) and the native fail-safe timer behave as the manual describes (`spikes/live-router/RESULT.md:21-23`, probes 7, 7b and 8, are marked NOT-RUN).
- Whether a real router executes a space-joined root key such as `{"system reboot":{}}`, and whether it accepts an empty object at a namespace (the raw request rules in `docs/SECURITY.md` are written to be safe either way).
- Whether the members of a real LAN bridge are `include` or `inherit` lines, and whether a real `show interface` answer is keyed by interface id (`crates/kcc-migrate/src/rules.rs`).
- Whether a real router refuses an `include` of an unknown member, accepts WireGuard leaves on a bridge, or deletes `Bridge0` (`crates/kcc-domain/src/interfaces/guard.rs`).
- The shape of a real `show running-config` answer (`crates/kcc-domain/src/firewall/read.rs:73-84` reads it as text) and whether the router accepts every abbreviation the catalog allows.
- `crates/kcc-migrate/src/interface_names.rs:4` decides whether an interface name is physical or logical with a name-shape heuristic taken from the documentation. The unit test pins the documented shapes only.
- The default `[outbound] argon2_max_iterations = 16` (`crates/kcc-app/src/settings.rs`) is not verified on a real KeeneticOS 5.2 router. If a real router asks for more than 16 Argon2 iterations at ndw4 sign-in, sign-in fails with "router authentication cost exceeds local policy" until the operator raises the setting.
- `crates/kcc-domain/src/configuration.rs:109-114`: the recovery mode for a router that reports no system mode assumes that 4.3 and 5.0 report a boolean `fail-safe.active` in `show last-change`. This is from the documentation. If it is wrong, kcc refuses the change with `router_mode_unknown`, which is the safe direction.

## Entware: unverified on hardware

None of the Entware work has run against a real router. These facts rest on the manuals and the fake router (and a fake Entware SSH server). The owner-run suites in `crates/kcc/tests/live_entware.rs` are meant to check them, each with `cargo test -p kcc --test live_entware -- --ignored --exact <name>`:

- `live_entware_probe` (read-only): needs `KCC_LIVE_URL`, `KCC_LIVE_LOGIN`, `KCC_LIVE_PASSWORD_FILE`, `KCC_LIVE_ALLOW_SERIAL` and `KCC_LIVE_TARGET_CONFIG`. It records `show media`, `show components list`, `show rc` `opkg`, `show version`, `kcc entware status` and the shape of one `show log` record.
- `live_entware_setup`: the same variables plus `KCC_LIVE_ALLOW_WRITE=1`, `KCC_LIVE_ENTWARE_SETUP=1` and `KCC_LIVE_ENTWARE_DRIVE` (the `opkg disk` argument of a spare drive, exactly as `kcc entware status` lists it). It installs Entware on that drive, never saves, and records the installer's log lines.
- `live_entware_ssh`: the base variables plus `KCC_LIVE_ALLOW_WRITE=1` and `KCC_LIVE_ENTWARE_PASSWORD_FILE` (the Entware root password; the installer's default is `keenetic`), and optionally `KCC_LIVE_ENTWARE_PACKAGE` (default `nano`, which must not be installed before). It probes port 222, then 22, enrols, lists, installs and removes the package, checks one service and always revokes kcc's key.

All three need a `test_device = true` profile named by `KCC_LIVE_TARGET_CONFIG` and an allow-listed serial (see the live env contract in `AGENTS.md`); a missing variable logs `live-skip:<reason>` and the test passes, so a green run without evidence files in `.omo/evidence/live-entware-*.json` proves nothing. Each line names the check:

- Component ids `opkg` and `ext`, and whether `components list` also shows components that are not installed. Check: `live_entware_probe`.
- The real `show media` fields (label, uuid, `initialize-supported`). Check: `live_entware_probe`.
- Whether `show rc` returns the `opkg` settings in the shape the fake router uses. Check: `live_entware_probe` (only with Entware set up; the suite reads, it does not remove).
- The install log markers on 5.x, and the `Opkg::Manager` component tag of the installer's lines. Check: `live_entware_setup` records them.
- SSH port 222 against 22. Check: `live_entware_ssh` tries 222, then 22.
- The `/opt/etc/dropbear/authorized_keys` path. Check: `live_entware_ssh` (a passing bootstrap). Its permissions are not read back by any suite; the enrolment script sets them (`chmod 700` on the directory, `600` on the file) and that stays unverified.
- Whether `dropbearkey -y -f /opt/etc/dropbear/dropbear_ed25519_host_key` prints the key kcc pins (the Web page and the guides send the administrator to it for the out-of-band check), and whether Entware's dropbear leaves a `dropbear_ed25519_host_key.pub` file on the drive. Check: compare the fingerprint `live_entware_ssh` records with the router's own; no suite does it.
- That `grep`, `mv`, `chmod`, `touch`, `mkdir` and `printf` exist in the Entware exec environment (kcc sets `PATH` explicitly). Check: `live_entware_ssh` (a successful bootstrap implies them; a failure reports the exit code).
- The init.d actions and exit codes per `rc.func`: `check`, 8 when the service is disabled, 255 on failure. Check: `live_entware_ssh` runs `services list` and `check` of the first service; no suite exercises exit 8 or 255.
- The raw `show log` record shape, and the `component` and `process` prefixes that Entware services produce (the installer's prefix is recorded by `live_entware_setup`). Check: `live_entware_probe` records one record's shape; no suite reads a service's log.
- That `opkg chroot` breaks kcc's paths, so kcc refuses while it is on. No live suite turns chroot on (it would cut SSH management); the refusal is proven only against the fake.
- Whether dropbear kills the running command when the channel closes. No live suite checks it.
- NetcrazeOS parity: that all of the above hold on Netcraze routers. Check: run the three suites against a Netcraze test router; no suite is specific to it.
- Whether `media initialize ext4` is accepted as `media <name> initialize ext4`, what `show media` reports while it runs, and whether a router that already shows ext4 answers the old filesystem right after accepting it (`storage::wait_initialized`, `crates/kcc-domain/src/storage.rs:203`, returns on the first read that shows ext4, so it could return before the wipe). No suite runs it: `live_entware_setup` needs a drive that is already prepared.
- Whether the router's `show rc` returns an `opkg` object after every opkg setting is removed (the read-back of a removal expects one: `PresencePredicate::Absent` in `crates/kcc-domain/src/entware/writes.rs:116`). No suite removes Entware.
- Whether the router matches `opkg disk` labels and medium ids case-insensitively. kcc's guard compares ids and labels case-sensitively but uuids case-insensitively (`crates/kcc-domain/src/storage.rs` `admit`, `entware/drives.rs` `resolve`), and when one medium's label equals another's uuid the uuid wins; an ambiguous label or a duplicated uuid resolves to no drive, so the guard is off for it. kcc's own planners never write such an `opkg disk`; a hand-made one would not be guarded. Hardening: compare ignoring ASCII case and treat every matching medium as the Entware drive.
- Whether the real router's `show log` always answers JSON. The setup treats a text reply (the fake's answer for an empty log) as an empty log, so a router that always answers text makes the job time out with `MarkerMissing` (fails closed), and `service_log` returns an empty list for a text reply, which a surface cannot tell from "no records".

## Entware and MCP sign-in: known residuals

Found while building and reviewing the Entware and MCP work. None is a security hole; each stays open for the reason given. Live checks are named in "Entware: unverified on hardware" above.

### Entware enrolment and SSH

- Re-bootstrapping an Active router saves a new key and marks the record Pending before the router is contacted (`crates/kcc-domain/src/entware/ssh/enrol/install.rs`, `run`). One wrong password, an unreachable router or a host-key mismatch demotes a working enrolment and replaces the local key; kcc's old line stays on the router until a new probe and bootstrap succeed. The Web asks for a ticked box, the CLI for `--yes`, and the guide says so; a design that keeps the old key until the new one works would change the plan's order of steps.
- An audit append failure in an SSH flow is logged at WARN and does not change the step's result (`entware/ssh/report.rs`). Failing closed would need the workflow's `audit_pending` style. A dropped request future (a client that disconnects, the MCP read bound of 90 s) leaves no audit entry for a command that already reached the router; a drop guard that queues a `cancelled` entry would close it.
- `set_port` and `set_enabled` (`crates/kcc-domain/src/entware/ssh/enrol.rs:258,278`) are not audited, the plan's event list having none for them; with `disable` they take the router write lease, so a running 15-minute setup job refuses them with RouterBusy.
- Sealed SSH files are read with an unbounded `fs::read` (`crates/kcc-app/src/entware_ssh.rs:194`); a 64 KiB cap would bound a damaged or planted file. `forget` leaves the `.<id>.*.tmp` crash temporaries, and a directory planted at `<id>.ticket.sealed` makes it fail (both need write access to the state directory). A ticket's expiry is wall-clock time, so a clock stepped back extends it. A Web delete whose `forget` fails shows success and logs at error; the CLI exits 1 after the profile is gone. An inner-record malformed JSON path has no test (reachable only with the master key).
- The `authorized_keys` scripts follow a pre-planted `/opt/etc/dropbear/authorized_keys.kcc` symbolic link (`crates/kcc-ssh/src/command.rs`): planting it needs root on the drive, so it crosses no boundary. A leading `rm -f` would close it, but the scripts are fixed character for character by the plan.
- `ops::update` treats a non-zero `opkg update` exit as `UnexpectedOutput`; the fake has no failing update, so no test pins the rule. `ops::job::start` audits nothing when it refuses a caller without `Destructive` before the job starts (the surfaces audit their own refusals), and `service_log` is not audited (an RCI log read like the others). `pool.acquire` waits without a bound, so surfaces put their own deadline on reads (25 s) while a 600 s mutation holds the router's session. A service's exit 8 from `stop` maps to `ServiceDisabled`. `Package.version` can carry control characters from the router: the CLI and MCP strip them and the Web escapes its output.
- The masker for service log records is the config-text masker `kcc_config::mask::redact_text`: for a role without `RevealSecrets` it leaves `password=<x>`, `login token <x>` and `ip http password <x>` visible. A log-specific rule belongs in `kcc-config`. `service_log` returns an empty list for a non-JSON reply, so a surface cannot tell no records from an unreadable log.
- russh-cryptovec calls `mlock` and `munlock` on every key buffer and ignores failures, and russh logs through the `log` crate, not `tracing`. The container's seccomp profile (`deploy/podman/seccomp-kcc.json`) has the default action `SCMP_ACT_ERRNO`, so a missing allowance makes the calls fail with an error russh ignores instead of killing the process; the regenerated profile lists them (the container e2e of todo 18 runs the SSH leg under it and its trace showed both). kcc installs no `log` bridge of its own (no `LogTracer` in `crates/*/src`); whether the kit's subscriber forwards `log` records is not verified, and the byte tests capture them through tracing-subscriber's `tracing-log` feature to prove no secret passes.
- The container's seccomp profile now allows `ioctl` without an argument filter, because the traced `FIONBIO` calls (non-blocking sockets for the loopback JWKS listener and the listener health probe) share the syscall with the terminal probe; `cargo xtask seccomp gen` has no argument filters. Restricting `ioctl` to `FIONBIO` and `TCGETS` would need a generator feature.
- The Web, CLI and MCP each build their own `SshServices` and session pool (`kcc-web/src/system_pages/entware_ssh.rs:87`, `kcc/src/cli/dom_entware_ssh_gate.rs:92`, `kcc/src/server_services.rs:174`), so the one-session-per-router and four-in-all limits hold per front end, not per process.
- MCP reports every `EntwareError::Ssh` and `RevokeFailed` as `router_unreachable` (`crates/kcc-mcp/src/domains/write/entware_ssh.rs:269`), host-key mismatch and rejected sign-in included, because `kcc-mcp` may not depend on `kcc-ssh`; the audit entry keeps the exact reason. `kcc_job_status` needs only `Read` to read an `entware.ssh.*` job record, whose failure message may name the package.

### Entware setup, settings and pages

- The setup commits every staged component change, including ones queued before it (`show components pending` need not be empty); a "components pending" refusal would be a plan change. The setup's preflight reports unsaved changes and a running fail-safe after the installer, drive, disk and component checks, which changes only which error comes first. `DriveChoice::InternalStorage` is accepted whenever Entware is possible (the status model has no internal-storage flag), and `SetupFailure::CancelledBeforeInstall` has no test. Direct POSTs of chroot, time zone, DNS override, startup script and remove on a router where Entware is not possible (the fake NC-3013, for example) are accepted, because the planners do not check the status.
- The Entware page region is not read again when the setup job ends: the done line offers Save, and a reload shows the new settings. The second acknowledgement for the drive Entware runs from is a query flag (`entware_ok=yes`) that a crafted same-session POST can carry; the household DNS sentence stands beside the control, not inside the typed-name dialog. The default-password warning shows only in the enrolment answer (the record keeps no flag), and an unreadable SSH record shows neither Revoke nor Forget here (a direct POST to `/disable` works). A direct `probe` POST with SSH management off still reads the host key.
- The shared typed-name dialog stays open over a started job on the Components page (`crates/kcc-web/src/system_pages/component_commit.rs`, `commit`; the Entware setup closes it with `respond::close_dialog`). Its initial focus is on Close, not the password field, and its input edge is faint in dark mode.
- CLI: an empty or newline-only password file sends one empty-password attempt (shared with `router add`), a BOM and surrounding spaces count as part of the password, `--json` does not print the Active re-bootstrap and `router remove` notices (`--yes` is still required), after `ssh disable` the key line stays on the router and `router remove` no longer warns, and a stalled RCI makes the SSH commands exit 6 with the generic RCI text after 10 s. The exit-4 headline "rejected before anything was sent" also prints for an unknown package or service, although one listing was read. The chroot warning prints before a busy refusal. The `kcc` CLI and `kcc serve` need a main-thread stack of about 768 to 784 KiB (measured with `ulimit -s`; 776 KiB passes and 768 KiB overflows for `kcc serve` with OAuth), against Windows' 1 MiB: every new command family and `block_on` arm raises it, so box big futures and re-measure.
- MCP: `acknowledge_entware_drive` sits on the shared housekeeping input, so it appears in `kcc_logging_write` and `kcc_schedules_write` and is accepted there without effect. JSON schemas carry no `maxLength`. The tool-count cap in `crates/kcc-mcp/src/tests/gates.rs:74` (`tools().len() <= 72`) is exactly met by today's 72 tools; the next tool needs a new cap.
- `kcc_job_cancel` for an Entware job now needs `Destructive` on the router; other job kinds keep `Write`.

### MCP settings and listeners

- A `ManageMcp` role below `admin` cannot hand out roles it does not cover, but a mapping that names a role that does not exist yet is skipped by the ceiling and would be handed out if such a role is created later; the CA upload ceiling is checked once by the Web handler (settings changes re-check at commit); the kit trusts the uploaded identity provider bundle in addition to its built-in roots; `allowed_algorithms` empty accepts RSA tokens (the kit default, ignored under D-RSA); the issuer is kept as a URL, so a bare host gains a trailing `/`; the JWKS host that does not resolve when the listener is built passes the pre-screen. All are documented in `docs/SECURITY.md`.
- The dedicated listener's self-signed certificate is made once (`crates/kcc/src/server_tls_dedicated.rs`, `ensure`), so a later change of `bind` or `public_url` keeps the old names until its files are deleted; the pinned health check passes while clients that check names fail.
- The supervisor's `Termination::install()` runs before tracing starts, so its "cannot install" warning is never printed. The test for a restart that cannot bind again (M8) runs only on hosts with a route to 192.0.2.1 and logs `live-skip` elsewhere.
- A live apply is unaudited when the request future is dropped after hand-over (`crates/kcc-web/src/admin_mcp/flow.rs`); an empty reset candidate is answered saved and audited as `success` with `changed: []` and bumps the revision; the restart progress is one global slot that races between concurrent restarts; a `kcc serve` stop during a restart leaves the page at "restarting" until its poll deadline, which then shows the timeout; the refresh lifetime shows as `7days`.
- `KccMcp` keeps the `get_tool` that the rmcp `#[tool_handler]` generates ungated, so a tool a tightening removed still resolves its input schema there; the call itself is refused. Gate it if a later rmcp dispatches through `get_tool`.
- The persistence layer parses state files into `serde_json::Value` first, so a duplicate key in a state file (for example `"read_only"` twice) is accepted with the last value winning, for every state document (`mcp_settings.json`, `roles.json`, `api_keys.json`).
- A hand-edited timestamp of year 10000 or later makes `humantime`'s `Display` fail: `Timestamp::at` now returns `None` for it, but `crates/kcc-web/src/config_page/backup_rows.rs:150` (`stamp`) still calls `.to_string()` on it and would panic on a backup file whose name carries such a time (a planted file; it needs write access to the state directory).

### kcc sign-in (OAuth) and client certificates

- The fair per-source eviction of pending authorization requests still yields to 1024 or more distinct sources (an IPv6 /54 is enough): the store is bounded and evicts the oldest request. A "refuse new requests when full and every source holds one" policy would keep live requests at the cost of refusing new sign-ins during a flood. The limiter's counters are per address, held as keyed hashes in memory. Listed as a limit in `docs/SECURITY.md`; no live test, the flood is proven by `serve_oauth` on Linux only (127.0.0.0/8 aliases).
- A replayed code does not revoke the grant already issued from it (RFC 9700 recommends it), reuse detection keeps 16 rotated refresh hashes (`MAX_PREVIOUS`, `crates/kcc-app/src/mcp_auth/grants.rs:33`; an older reused token is refused as unknown but does not revoke the family), and the 50-client limit counts admin-registered clients, so unauthenticated registration from several addresses can block an administrator's pre-registration for up to 24 hours (exempting administrators is open). The limiter shows one cosmetic empty entry when full.
- The per-call cache of `users.json`, `mcp_oauth_grants.json` and `mcp_oauth_clients.json` is keyed by (inode, modification time, size) (`crates/kcc/src/server_mcp_auth/principals.rs`): a same-size, same-mtime in-place rewrite is not seen. Every kcc writer renames, so only someone with write access to the state directory can produce it; adding the change time on Unix would close it. A symbolic link in place of a state file is followed (the `StateStore` behaviour), which also needs state directory access.
- Deleting an account does not revoke its grants: kcc refuses their calls, but the Connections tab lists them under the old name until revoked. An account that must change its password cannot resume the client's pending request after the change. `/oauth/token` checks a refreshed grant's resource after rotating, so a listener that stopped serving the resource leaves the grant dead until it expires. The CLI exits 2 for "nothing to revoke", under the headline "The command line is incomplete or invalid" (a dedicated not-found class would be a new exit code).
- Client certificates: the probe could prove the right CA is loaded by comparing the CertificateRequest root hints with the stored CA subjects. Audit actor ids are cut at 64 bytes and the kit allows Unicode letters in a name. A certificate with no CRL distribution point under a CA with none is never revocation-checked. A browser with a certificate from another CA is refused at TLS on an optional main listener. The Web decides "in use" for a CA from the effective settings and the supervisor from the running generations; both directions are safe.
- The kit's authorization-server proxy, CIMD, key rotation and the rest of the list above are open features, not residuals. The signing key is made once and never rotated.
- Admin pages: the shared admin `.panels` grid leaves empty space under the shorter card of a row; the tab strip scrolls sideways on phones and is cut off at 390 px ("Notif...") with only a thin scrollbar as a cue (pre-existing). Native file inputs of the VPN import dialog (`kit_form.html`) and of the migration source step (`migrate_source.html`) overflow 320 px (pre-existing). `crates/kcc-web/src/admin.rs`, `admin_shared.rs`, `admin_keys.rs`, `auth.rs`, `lib.rs`, `admin_mcp/upload.rs`, `kcc-app/src/mcp_settings/client_ca.rs`, `kcc-app/src/mcp_settings.rs` (495 lines), `mcp_settings/update.rs` (382), `mcp_auth/grants.rs` (381), `kcc-web/src/admin_mcp/upload.rs` (355), `kcc-testkit/src/entware_ssh.rs` and several test `support` modules are over the 250-line guideline.

## Final review of the Entware and MCP work: candidates

Seven final-wave reviewers read the Entware and MCP work and listed what they saw but did not call a finding. Each bullet names where it is and why it was not fixed. UI items were seen in a browser against the fake router and are not re-run here; code places were opened and match. ### Security-adjacent

- A token whose grant was revoked still completes the MCP `initialize` handshake (HTTP 200) until the JWT expires; every tool, resource and prompt call is refused at once (`forbidden`). Documented in SECURITY.md "Revocation latency". Closing it would mean refusing `initialize` too, which the per-call check design of todo 31 does not do. Owner decision pending.
- Every RCI POST, the Entware install POST included, is sent as `RequestKind::PostRejectedBeforeBody` (`crates/kcc-rci/src/engine.rs:355,372`), so one transparent replay is allowed after a router 401 (`crates/kcc-rci/src/session.rs:68,76`). The 401 proves the router refused it before reading the body, so the replay is safe by that contract; a literally non-replayable kind for the install POST would not rely on it. The plan item D-10a asked for the stricter kind, so either change the kind or record the choice as an owner-accepted amendment.
- The OIDC CA upload is not treated as safety-reducing: it asks for no password re-entry, unlike the other identity provider fields, which `reduces_safety` lists as `KeyPath` entries (`crates/kcc-app/src/mcp_settings/update.rs:281-318`; the upload goes through `crates/kcc-web/src/admin_mcp/upload.rs`). A CA that signs the identity provider's key set decides who may sign in, so it arguably belongs in the same class.
- The ed25519 seed of a generated SSH key comes from `rand::rng()` (`crates/kcc-ssh/src/keys.rs:117`), a CSPRNG seeded from the operating system. The guidelines ask for the operating system source for key material, and `mcp_auth` already uses ring's `SystemRandom`. Switching to `rand::rngs::OsRng` or `getrandom` is a one-line change.
- The generated MCP signing key is dropped without wiping: the PKCS#8 document and its base64 copy in `crates/kcc-app/src/mcp_auth/signing.rs:215-229` are plain values, while the loaded path uses `Zeroizing`. Memory hygiene only.
- `crates/kcc-ssh/src/transport.rs:233-245` tries each admitted address with a bare `TcpStream::connect` and no per-address bound, so a black-holed first address spends the whole connect timeout and later admitted addresses are never tried. Fails closed; the fix is a bound per attempt.
- The protected-resource metadata `resource` follows the request host (`http://127.0.0.1:<port>/mcp` while the issuer says `localhost`). Both names are accepted for the same listener, other hosts and paths get `invalid_target`, and no security effect was seen. It could confuse client setup, so the setup guide could say which name to use.
- An API key may be named `kcc-account`, the reserved role's name (`is_valid_key_name`, `crates/kcc-app/src/api_keys.rs:141`, checks only characters and length). The key keeps the role it was created with, and the reserved role itself cannot be created, so no impersonation path was found. Cosmetic, but a reserved-name check would remove the doubt.
- `/ui/admin/mcp` matches by prefix, so `/ui/admin/mcpX` also asks for `ManageMcp` (`crates/kcc-web/src/authz.rs:267`). That is stricter than needed, not looser; an exact segment match would be cleaner.

### Correctness and UX

## Upstream (rmcp-server-kit)

- `[server] max_concurrent_requests` is unset by default (`docs/CONFIG.md`; `crates/kcc/src/server.rs:59-67` passes the table to the kit), and the kit logs that in-flight requests are unlimited. A default bound would cap held requests besides the per-router lease. Whether the kit should default it, or kcc should ship a value, is the maintainer's call.
- The kit's HTTP listener has no header read timeout, so a connection that sends a request line and then goes silent stays open for more than 70 seconds. It cannot be set from `crates/kcc/src/server.rs:59-67`.
- The kit logs a transport-level 403 (an MCP request refused before any tool runs) itself; it is not written to `audit.jsonl` (`crates/kcc-mcp/src/support/audit.rs`, module doc, audits tool-level refusals only).
- The kit inserts `Cache-Control` on every response or on none, so kcc turns it off to keep the immutable policy of hash-addressed assets (`crates/kcc-web/src/csp.rs`), and the kit's own routes (`/mcp`, health, version) go without it. A mode that sets the header only when the route has not set one would let kcc keep `no-store` on those routes (project overlay deviation 5).
- RUSTSEC-2026-0542 (`humantime`) and RUSTSEC-2026-0543 (`chrono`) are unmaintained notices, ignored in `deny.toml` and `.cargo/audit.toml` by owner decision on 2026-11-18 until 2027-02-18. kcc also uses them directly (kcc-app and kcc-web for humantime; kcc-telemetry for chrono), but rmcp-server-kit, rmcp and schemars also require them, so removing kcc's own use would not clear the notice. The fix is upstream (a release that stops depending on `chrono` and `humantime`), after which the ignore entries are removed.
- RUSTSEC-2023-0071 (`rsa` 0.9.10, Marvin attack) and RUSTSEC-2026-0387 (`crypto-bigint` 0.5.5, timing variability) come only through `jsonwebtoken` 11.1.0 (`rust_crypto`), which rmcp-server-kit 3.21.1 pins for its `oauth` feature. Both are ignored in `deny.toml` and `.cargo/audit.toml` by owner decision on 2026-11-22 until 2027-02-18, because kcc and the kit only verify signatures with public keys and kcc signs its own tokens with Ed25519 through `ring`. When an rmcp-server-kit release moves to `jsonwebtoken` 12 (`rsa` 0.10, `crypto-bigint` >= 0.7.6), remove both ignore entries, the duplicate entries that name `jsonwebtoken` 11 in `deny.toml` `skip` and `clippy.toml` `allowed-duplicate-crates`, and their `cargo vet` exemptions.
- `docs/rust-guidelines/UPSTREAM.md` lists the guideline changes the owner still has to propose by hand.

## Known gaps

- `crates/kcc/src/server.rs:121-130`: on SIGTERM with nothing in flight, `kcc serve` exited about 4.4 s after it logged "jobs drained". Traced to the router log collectors: their waits between reads (the 5 s stream interval, the 30 s poll interval) could not be cancelled, and the collectors were stopped one after another, so the delay grew with the number of routers. The waits now end on cancellation and all collectors stop together (`crates/kcc-telemetry/src/logs/service.rs`, `runtime.rs`). Not re-measured on a `kcc serve` process; if a delay remains with `[logs]` disabled, its cause is elsewhere.
- The CLI has no SIGINT or SIGTERM handling during a safety bracket (`crates/kcc/src/cli/change.rs:228`). If the process is killed, the router's own timer restores the saved configuration; `kcc serve` and `kcc mcp stdio` do wait for their brackets, on SIGTERM and SIGINT as well (and `kcc mcp stdio` on stdin EOF).
- The Web standalone rollback is not mode-aware (`crates/kcc-web/src/config_page/safety.rs:133-170` and `with_timer` at `:194`): on a router in scheduled-reboot mode it refuses ("not armed") instead of rebooting like the CLI does.

- `crates/kcc-web/src/dns_vpn/dns_checks.rs:82` builds its change with a fixed `Risk::Write`; it is the only Web page that does not take its risk from the domain planner.
- The reboot, reset and mesh-restart actions (`crates/kcc-web/src/system_general.rs`, `net_mesh.rs`) ask for their confirmation only after the router context is read, because they plan first and let the shared submit step ask for the planned risk. A confirmation that does not depend on the plan (`Submission::confirming`) would ask before any router request.

- The `Risk::Management` branch of the scheduled policy switch (`crates/kcc/src/server_schedules/actions/policy.rs:94`) maps a failure with a possibly armed timer to a plain `failed` and frees the lease. Unreachable today, since policy plans are `Risk::Write`. ## Decisions kept on purpose

- The session keepalive was removed. It was code in `crates/kcc-rci/src/session.rs` meant to send a periodic request so an idle router session would not expire, but nothing ever started it. If a long-lived server needs idle sessions kept open, it has to be rebuilt and wired in.
- The Argon2 budget for the ndw4 sign-in math is fixed at one derivation at a time (`crates/kcc-rci/src/ndw4_keys.rs:17`); the setter for it was removed because nothing called it. A fleet that signs in to many routers at once therefore derives their keys one after another.
- Two small helpers were not replaced by crates: the edit-distance function (`damerau_levenshtein` in `crates/kcc-catalog/src/validate/suggest.rs:36`, instead of `strsim`) and the router network check (`AllowedNetwork` in `crates/kcc-rci/src/outbound.rs:38`, instead of `ipnet`). Both are short, tested and need no new dependency.
- An interactive apply (Web wizard, MCP, CLI) frees the router's lease as soon as its preparation fails, also when the fail-safe timer may still be armed (`ArmUnconfirmed`, or `FinishFailed` before any line was sent). The operator is told that the timer may be armed, and a retry or kcc's own fail-safe steps need the lease; a CLI process frees it when it exits anyway. Only a scheduled preset, which nobody watches, keeps the lease until the timer has run out (`ApplyOptions::hold_armed_failure`, set in `crates/kcc/src/server_schedules/preset/finish.rs`).
- Two glob matchers with different semantics exist, and neither is shared: `crates/kcc-migrate/src/rules.rs:822-860` (rule globs: case-sensitive, a segment may end in `*`) and `crates/kcc-migrate/src/presets/glob.rs:4-52` (preset group patterns: case-insensitive, a segment may have a `*` in the middle, plus a catalog-path matcher). Merging them would change what existing rules and presets match.

## CI and test infrastructure follow-ups

- `Applier::start`'s `done` receiver resolves before the job has ended and freed the router's write slot (`crates/kcc-migrate/src/apply.rs:101-160`, `crates/kcc-app/src/jobs.rs`), so a caller that starts another write job on the same router straight after the verdict can be refused as busy. The MCP apply tools and one migrate test now wait for `JobRunner::ended`; the Web wizard (`crates/kcc-web/src/wizard/launch.rs`) probably has the same window (not tested). Fix it once in the engine by letting `done` resolve after the job ended.
- Paused-clock tests that still reach their fakes over loopback TCP may be flaky on macOS: the fake Loki, Elasticsearch and silent-sink listeners and the sink clients in `crates/kcc-telemetry/tests/logs.rs`, `logs/collection.rs`, `logs/bounds.rs` and `logs/pipeline.rs`. The router side is already on the Unix-socket seam; the sink legs need the same hook on `crates/kcc-telemetry/src/logs/sink_http.rs` and a `serve_local` for `fake_loki` and `fake_elasticsearch`.
- The Windows CI leg depends on `.github/scripts/deelevate.ps1` (launcher method `filtered`: a restricted token whose elevated groups are deny-only). The runner token is elevated by default and kcc refuses an elevated token by design, so the launcher fails the step if the child is still elevated. If GitHub changes the image's token, the launcher's `-Method` probe in `.github/workflows/probe.yml` (`token_probe`) shows which methods still work.
- Two SIGHUP-reload tests are unix-only (`crates/kcc/tests/metrics_serve/runtime.rs`, `crates/kcc/tests/serve_refresh.rs`): Windows has no SIGHUP, so reload-on-signal is untested there.
- Windows tests that read the platform state directory set `LOCALAPPDATA` and `APPDATA` in four spawn helpers. A new spawn helper that clears the environment must do the same, and keep `SystemRoot`.
## Notifications and scheduled actions: not in v1

- Quiet hours.
- Per-user subscriptions.
- Channels other than Telegram.
- Clearing a client's policy on a schedule.
- Scheduled access permit or deny (routers schedule it themselves).
- Mirror-mode and management-line presets on a schedule.
- The metadata-address check for log sinks (`kcc_rci::outbound::never_admitted` is applied to Telegram only).
- A reboot sent by another process (the CLI, `kcc scheduled run-now` from the CLI included) does not mute down/up messages, and a CLI run-now sends no Telegram outcome.
- A server starting while a CLI run-now is in progress reports that run once as interrupted (the run ledger still records its true outcome).
- Whether Telegram's 4096 limit counts characters or UTF-16 units (kcc keeps both within it).
- Router audit events from other processes (a CLI change) are not notified.
- The public-CA TLS path to Telegram is exercised only by the owner-run live suite.
- A router in `ScheduledReboot` safety mode mutes its down alerts for 15 minutes after any bracket step.
