# Backlog

Open items that do not block a release. One line each: where it is (`file:line`) and why
it stays open. Line numbers are those of the tree at the time of writing.

## Not proven on hardware

No live suite has run against a real router yet: every `live_*` test logs `live-skip` and
returns, and `docs/FIRMWARE.md:10` still says "live verification not yet run" for 5.1 (the
firmware doc test accepts that text). Until a test router is available, these behaviors
rest on the manuals and the fake router only:

- The command forms the planners and the catalog build from the manuals have never reached a real router. These are the order of `ipv6 route <prefix> <interface> <gateway>` and the `ip route` metric on 4.3, the `system log server` and `wireguard peer endpoint` forms, planning an interface as `interface down`, the `interface <name> vlan-id` line the segments send, the host-name form of `ip http proxy upstream` (typed in the catalog as a host name), the firewall reorder form `access-list <name> rule <index> order <position>`, and `no ip dhcp pool <name> dns-server` (the fake router's rule for it was relaxed to accept the bare leaf).
- A same-value rewrite of a router account, PPP or Wi-Fi secret is reported as "did not change" because the md5 and `ns3` encodings are deterministic and kcc cannot tell it from an ignored write. This follows from the algorithms and the fake router, not from hardware.
- The end-to-end driver (`deploy/podman/e2e.sh`) was proven against the fake router and, in container mode, against a podman image. A real `workflow_call` run of the release workflow, a tag push and the required status checks (set in GitHub) cannot be exercised from a checkout.

- The Windows path for sealed credentials and key files (owner-only ACLs, `crates/kcc-app/src/persist/windows_acl.rs`, checked by `crates/kcc-app/tests/windows_acl.rs`) runs in CI on GitHub's `windows-latest` runner (Windows Server 2025), as does the whole test suite, under a non-elevated token; the macOS leg runs too. Still not verified: a real user's Windows machine (domain-joined accounts, redirected profiles, antivirus, non-NTFS volumes) and a real macOS or Windows deployment of `kcc serve`.
- Whether a real router answers 404 to `GET /rci/system/reboot`, and whether the scheduled-reboot fallback (extender, access-point and repeater modes) and the native fail-safe timer behave as the manual describes (`spikes/live-router/RESULT.md:21-23`, probes 7, 7b and 8, are marked NOT-RUN).
- Whether a real router executes a space-joined root key such as `{"system reboot":{}}`, and whether it accepts an empty object at a namespace (the raw request rules in `docs/SECURITY.md` are written to be safe either way).
- Whether the members of a real LAN bridge are `include` or `inherit` lines, and whether a real `show interface` answer is keyed by interface id (`crates/kcc-migrate/src/rules.rs`).
- Whether a real router refuses an `include` of an unknown member, accepts WireGuard leaves on a bridge, or deletes `Bridge0` (`crates/kcc-domain/src/interfaces/guard.rs`).
- The shape of a real `show running-config` answer (`crates/kcc-domain/src/firewall/read.rs:73-84` reads it as text) and whether the router accepts every abbreviation the catalog allows.
- `crates/kcc-migrate/src/interface_names.rs:4` decides whether an interface name is physical or logical with a name-shape heuristic taken from the documentation. The unit test pins the documented shapes only.
- The default `[outbound] argon2_max_iterations = 16` (`crates/kcc-app/src/settings.rs`) is not verified on a real KeeneticOS 5.2 router. If a real router asks for more than 16 Argon2 iterations at ndw4 sign-in, sign-in fails with "router authentication cost exceeds local policy" until the operator raises the setting.
- `crates/kcc-domain/src/configuration.rs:109-114`: the recovery mode for a router that reports no system mode assumes that 4.3 and 5.0 report a boolean `fail-safe.active` in `show last-change`. This is from the documentation. If it is wrong, kcc refuses the change with `router_mode_unknown`, which is the safe direction.

## Upstream (rmcp-server-kit)

- `[server] max_concurrent_requests` is unset by default (`docs/CONFIG.md`; `crates/kcc/src/server.rs:59-67` passes the table to the kit), and the kit logs that in-flight requests are unlimited. A default bound would cap held requests besides the per-router lease. Whether the kit should default it, or kcc should ship a value, is the maintainer's call.
- The kit's HTTP listener has no header read timeout, so a connection that sends a request line and then goes silent stays open for more than 70 seconds. It cannot be set from `crates/kcc/src/server.rs:59-67`.
- The kit logs a transport-level 403 (an MCP request refused before any tool runs) itself; it is not written to `audit.jsonl` (`crates/kcc-mcp/src/support/audit.rs`, module doc, audits tool-level refusals only).
- The kit inserts `Cache-Control` on every response or on none, so kcc turns it off to keep the immutable policy of hash-addressed assets (`crates/kcc-web/src/csp.rs`), and the kit's own routes (`/mcp`, health, version) go without it. A mode that sets the header only when the route has not set one would let kcc keep `no-store` on those routes (project overlay deviation 5).
- RUSTSEC-2026-0542 (`humantime`) and RUSTSEC-2026-0543 (`chrono`) are unmaintained notices, ignored in `deny.toml` and `.cargo/audit.toml` by owner decision on 2026-11-18 until 2027-02-18. kcc also uses them directly (kcc-app and kcc-web for humantime; kcc-telemetry for chrono), but rmcp-server-kit, rmcp and schemars also require them, so removing kcc's own use would not clear the notice. The fix is upstream (a release that stops depending on `chrono` and `humantime`), after which the ignore entries are removed.
- RUSTSEC-2026-0592 (`url` 2.5.8, stack overflow in `Url::origin()` on a nested `blob:` URL) is ignored in `deny.toml` and `.cargo/audit.toml` by owner decision on 2026-11-22, TEMPORARILY: the fix `url` >= 2.5.9 was published 2026-11-20, inside the 3-day publish-age cooldown until 2026-11-23. kcc calls `Url::origin()` only on admin-entered values (`public_url`, `RouterUrl`), and rmcp-server-kit only on certificate-revocation URLs when mTLS revocation is configured. Remove both entries when `cargo update -p url` lands (review by 2026-11-24).
- `docs/rust-guidelines/UPSTREAM.md` lists the guideline changes the owner still has to propose by hand.

## Known gaps

- `crates/kcc/src/server.rs:121-130`: on SIGTERM with nothing in flight, `kcc serve` exited about 4.4 s after it logged "jobs drained". Traced to the router log collectors: their waits between reads (the 5 s stream interval, the 30 s poll interval) could not be cancelled, and the collectors were stopped one after another, so the delay grew with the number of routers. The waits now end on cancellation and all collectors stop together (`crates/kcc-telemetry/src/logs/service.rs`, `runtime.rs`). Not re-measured on a `kcc serve` process; if a delay remains with `[logs]` disabled, its cause is elsewhere.
- The CLI has no SIGINT or SIGTERM handling during a safety bracket (`crates/kcc/src/cli/change.rs:228`). If the process is killed, the router's own timer restores the saved configuration; `kcc serve` and `kcc mcp stdio` do wait for their brackets, on SIGTERM and SIGINT as well (and `kcc mcp stdio` on stdin EOF).
- The Web standalone rollback is not mode-aware (`crates/kcc-web/src/config_page/safety.rs:133-170` and `with_timer` at `:194`): on a router in scheduled-reboot mode it refuses ("not armed") instead of rebooting like the CLI does.
- `crates/kcc-web/src/page_kit/facts.rs:14`: the Web facts cache holds a router's catalog for 600 s, so a firmware change is noticed up to ten minutes late.
- `crates/kcc-web/src/dns_vpn/dns_checks.rs:82` builds its change with a fixed `Risk::Write`; it is the only Web page that does not take its risk from the domain planner.
- The reboot, reset and mesh-restart actions (`crates/kcc-web/src/system_general.rs`, `net_mesh.rs`) ask for their confirmation only after the router context is read, because they plan first and let the shared submit step ask for the planned risk. A confirmation that does not depend on the plan (`Submission::confirming`) would ask before any router request.
- The wizard finish routes still have three entry handlers for the migration (`/commit`, `/rollback`, `/{way}` in `crates/kcc-web/src/migrate_wizard/routes.rs:52-57`) and one for presets (`/{way}`, `crates/kcc-web/src/presets_page/routes.rs:79-82`). Making them one changes edge behavior (the content type of commit, the order of dialogs, the order of the unknown-way 404), so it needs a decision.
- The firewall page reads rules as running-config text (`crates/kcc-domain/src/firewall/read.rs`, `firewall`), while the CLI, MCP and the planner's read-back use `configured_list` (`show rc` JSON, IPv4 only, the targeted list alone; a rule in another form is kept as `ListedRule::Unstructured`). Two readers of the same data remain; unifying them would change the CLI's request count.
- Firewall rule read-back is a presence check (`crates/kcc-domain/src/firewall/change/verify.rs`): when the target state already holds before the write, it cannot tell an applied write from an ignored one. Adding a rule equal to one already in the list passes even if the router ignored the line, and removing one of two equal rules fails on the remaining copy. Counting equal rules before and after would close it; the VPN client secret read-back has the same limit (left with the VPN client work).
- Secret write read-back (`crates/kcc-app/src/workflow_credential.rs`) requires the stored `md5`/`ns3` payload of a router account, PPP or Wi-Fi password to change. That a real router stores the same payload again for the same password (so a same-value rewrite fails as unchanged) follows from the algorithms and the fake router, not from hardware.
- VPN credentials (`crates/kcc-domain/src/vpn_clients/secrets.rs`, `ConfigSecret`: L2TP/PPTP/SSTP passwords, IPsec and IKE keys, WireGuard obfuscation and preshared keys) are still read back for presence only, so an ignored write over a stored credential passes; `VerificationSpec::replaced` would cover them.
- `crates/kcc-domain/src/firewall/lists.rs:204-208` skips an interface binding whose direction is not `in` or `out`. The firmware only writes those two.
- The master key (`MasterKey::load_or_create`, `crates/kcc-app/src/secrets.rs:219`) is the plaintext root of trust: anyone who can read that file can open the state store. Podman's default file secret driver also keeps the deployed secrets unencrypted on the host (`deploy/podman/README.md`, Secrets). Wrapping the key with `systemd-creds` or a TPM is a possible future step.
- `ApplyNeeds::raw_restore` (`crates/kcc-domain/src/configuration/apply_needs.rs:13,27-31`, set by `restoring_raw`), the flag that adds `Destructive` for a raw restore, has no production caller yet; the Web raw restore holds `Destructive` through its own constant.
- One CLI refusal has no machine-readable handle: an absent firewall rule property prints a sentence with exit code 4 and no code (`crates/kcc/tests/cli_domain_writes/admin.rs:106` pins the exit code only).
- An MCP client that disconnects or cancels in the middle of a management change gets no reply for that call, but the bracket completes: rmcp 3.10 runs each request in its own detached task (`rmcp-3.10.0/src/service.rs:1629`, `tokio::spawn` at `:1352`) and kcc-mcp never reads the request's cancellation token, so nothing cancels the bracket and the disarm and its audit entries still happen (`an_mcp_bracket_outlives_a_disconnected_client` in `crates/kcc/tests/serve_bracket/disconnect.rs`). The kit's `[server] request_timeout` bounds only the time until the SSE reply starts (`rmcp-server-kit-3.21.1/src/transport.rs:2744-2751`), so it never cuts a running call: the reply arrives (`an_mcp_bracket_outlasting_the_request_timeout_answers`). ## Decisions kept on purpose

- The session keepalive was removed. It was code in `crates/kcc-rci/src/session.rs` meant to send a periodic request so an idle router session would not expire, but nothing ever started it. If a long-lived server needs idle sessions kept open, it has to be rebuilt and wired in.
- The Argon2 budget for the ndw4 sign-in math is fixed at one derivation at a time (`crates/kcc-rci/src/ndw4_keys.rs:17`); the setter for it was removed because nothing called it. A fleet that signs in to many routers at once therefore derives their keys one after another.
- Two small helpers were not replaced by crates: the edit-distance function (`damerau_levenshtein` in `crates/kcc-catalog/src/validate/suggest.rs:36`, instead of `strsim`) and the router network check (`AllowedNetwork` in `crates/kcc-rci/src/outbound.rs:38`, instead of `ipnet`). Both are short, tested and need no new dependency.
- An interactive apply (Web wizard, MCP, CLI) frees the router's lease as soon as its preparation fails, also when the fail-safe timer may still be armed (`ArmUnconfirmed`, or `FinishFailed` before any line was sent). The operator is told that the timer may be armed, and a retry or kcc's own fail-safe steps need the lease; a CLI process frees it when it exits anyway. Only a scheduled preset, which nobody watches, keeps the lease until the timer has run out (`ApplyOptions::hold_armed_failure`, set in `crates/kcc/src/server_schedules/preset/finish.rs`).
- Two glob matchers with different semantics exist, and neither is shared: `crates/kcc-migrate/src/rules.rs:822-860` (rule globs: case-sensitive, a segment may end in `*`) and `crates/kcc-migrate/src/presets/glob.rs:4-52` (preset group patterns: case-insensitive, a segment may have a `*` in the middle, plus a catalog-path matcher). Merging them would change what existing rules and presets match.

## CI and test infrastructure follow-ups

- `Applier::start`'s `done` receiver resolves before the job has ended and freed the router's write slot (`crates/kcc-migrate/src/apply.rs:101-160`, `crates/kcc-app/src/jobs.rs`), so a caller that starts another write job on the same router straight after the verdict can be refused as busy. The MCP apply tools and one migrate test now wait for `JobRunner::ended`; the Web wizard (`crates/kcc-web/src/wizard/launch.rs`) probably has the same window (not tested). Fix it once in the engine by letting `done` resolve after the job ended.
- Paused-clock tests that still reach their fakes over loopback TCP may be flaky on macOS: the fake Loki, Elasticsearch and silent-sink listeners and the sink clients in `crates/kcc-telemetry/tests/logs.rs`, `logs/collection.rs`, `logs/bounds.rs` and `logs/pipeline.rs`. The router side is already on the Unix-socket seam; the sink legs need the same hook on `crates/kcc-telemetry/src/logs/sink_http.rs` and a `serve_local` for `fake_loki` and `fake_elasticsearch`.
- The Windows CI leg depends on `.github/scripts/deelevate.ps1` (launcher method `filtered`: a restricted token whose elevated groups are deny-only). The runner token is elevated by default and kcc refuses an elevated token by design, so the launcher fails the step if the child is still elevated. If GitHub changes the image's token, the launcher's `-Method` probe in `.github/workflows/probe.yml` (`token_probe`) shows which methods still work.
- Two SIGHUP-reload tests are unix-only (`crates/kcc/tests/metrics_serve/runtime.rs`, `crates/kcc/tests/serve_refresh.rs`): Windows has no SIGHUP, so reload-on-signal is untested there.
- Windows tests that read the platform state directory set `LOCALAPPDATA` and `APPDATA` in four spawn helpers. A new spawn helper that clears the environment must do the same, and keep `SystemRoot`.
## Notifications and scheduled actions: not in v1

- Quiet hours.
- Per-user subscriptions.
- Channels other than Telegram.
- Clearing a client's policy on a schedule.
- Scheduled access permit or deny (routers schedule it themselves).
- Mirror-mode and management-line presets on a schedule.
- The metadata-address check for log sinks (`kcc_rci::outbound::never_admitted` is applied to Telegram only).
- A reboot sent by another process (the CLI, `kcc scheduled run-now` from the CLI included) does not mute down/up messages, and a CLI run-now sends no Telegram outcome.
- A server starting while a CLI run-now is in progress reports that run once as interrupted (the run ledger still records its true outcome).
- Whether Telegram's 4096 limit counts characters or UTF-16 units (kcc keeps both within it).
- Router audit events from other processes (a CLI change) are not notified.
- The public-CA TLS path to Telegram is exercised only by the owner-run live suite.
- A router in `ScheduledReboot` safety mode mutes its down alerts for 15 minutes after any bracket step.
