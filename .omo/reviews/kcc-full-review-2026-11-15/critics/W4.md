- reasoning:
  - **Permission needed:** `/ui/r/{r}/explorer/execute` falls to `Permission::Read`. The handler then re-checks only `command_permissions(risk)`. `show running-config` is `CommandKind::Show`, so its risk is `Read`, so only `Read` is needed. The built-in `viewer` role holds exactly that.
  - **Path to the page:** a Read request goes `read_root`, then `answered`, then `Rendered::body(body, reveal)`. A `Text` body is passed through untouched. A JSON body is passed through `mask`, which matches member *names* only, so string lines such as `"... wpa-psk ns3 <blob>"` survive. A truncated answer is also kept for download.
  - **The blobs are real secrets:** `kcc_config::ns3::decode` turns an ns3 blob back into the plaintext secret.
  - **The code knows this:** `preview::stored` and `firewall::read` run running-config text through `redact`/`ns3_redacted` before anyone sees it. The explorer and CLI read paths do not.
  - **Remaining inference:** the exact shape of the real RCI answer is unknown (`docs/BACKLOG.md:18`). It does not matter here, because neither a text answer nor JSON string lines are masked.
  - **Second vector, no shape inference needed:** `mask` skips a secret-named member whose value is an object and recurses into it. In `"password":{"ns3":"<blob>"}`, the inner key `ns3` is not a secret name, so the blob is shown. The fake router's `show interface` projection returns exactly this shape (`projection/interface.rs:66-69`), so a viewer running `show interface` would see the blob.
  - **Console claims hold:** a `RawRci` holder without `RevealSecrets` gets the same leak through the CLI read path. `more` is an `Action`, so its risk is `Write` and only `RawRci` is needed.
- severity: high. `RevealSecrets` is fully bypassed by the lowest built-in role, and the leaked ns3 secrets are reversible.

### W4-02 ADJUSTED
- checked: `advanced/jobs.rs:76-125,179-219`, `advanced/job_stream.rs:63-88,143-167`, `system_pages/jobs.rs:122-154,236-267`, `system_pages/diagnostics.rs:117-185`, `kcc-domain/src/diagnostics.rs:133-148,268-279`, `kcc-app/src/jobs/job_id.rs:26-69`, `kcc-app/src/jobs.rs:69-88,407`, `docs/rust-guidelines/overlays/domains/http-services.md` (grep).
- reasoning:
  - **No ownership check exists.** `explorer_job` and `followed` filter only on router and kind, and `JobRecord` has no owner field. Stop needs router scope only, plus `RawRci` for `explorer.raw.*` jobs. Both streams need router scope only.
  - **Ids are predictable.** An id is unix seconds (`jobs.rs:407`), plus the process id and 4 bytes of entropy that stay constant for the process, plus a global counter. One job of your own reveals the constant parts. Starting two of your own jobs brackets the counter and time of everyone else's.
  - **A viewer can start jobs.** Diagnostics are `Risk::Read`/`Permission::Read`, so a viewer can start one and learn the id format.
  - **What a viewer can actually reach is narrow:**
    - Stop: other users' diagnostics and `explorer.read.*` jobs (for example `show log`). All of these only read.
    - Not stoppable by a viewer: `explorer.raw.*` jobs need `RawRci`, and the component commit is filtered out of cancel.
    - Follow: shows ping/traceroute lines or an answer rendered with `reveal=false`, which a viewer could produce by running the same tool.
  - **The cited rule is unsupported.** The http-services overlay has no per-resource authorization rule.
- severity: low
- correction: This is a missing ownership check on read-only background jobs. A router-scoped viewer can cancel or watch other users' diagnostics and explorer read jobs, and the ids are easy to enumerate. Write jobs, raw jobs and the commit job are out of reach. The proposed fix (store the starting user, require a match or an admin permission) is sound.

**NEW: `mask` passes secrets through when the secret-named member is an object.** In `crates/kcc-web/src/page_kit/secret.rs:37-40`, a member with a secret name is masked only when its value is a scalar. Otherwise `mask` recurses, and the inner key `ns3` is not in `is_secret` (lines 16-29). So `{"password":{"ns3":"<blob>"}}` reaches the page unmasked for users without `RevealSecrets`. That covers the explorer read viewer and the RCI/CLI console viewers, through `Rendered::json`. The fake router's `show interface` answer has exactly this shape (`kcc-testkit/src/projection.rs:100-103`, `projection/interface.rs:66-69`), and `kcc-domain/tests/wan.rs:28` uses it too. A viewer running the Read command `show interface` in the explorer would therefore see the blob, with no need to guess the shape of the `show running-config` answer. The MCP redactor does this correctly: `kcc-mcp/src/support/shape.rs:207-239` replaces the whole member and also treats `ns3` as secret. Suggested fix: mask the whole member when its name is secret, whatever its type, and add `ns3` to `is_secret`.
