### W1-01 Disabling an account or changing its password from the CLI does not end its live Web sessions
- severity: medium
- kind: security
- rule: overlay http-services (authn/authz) + RUST_GUIDELINES.md §11 Security "Auth attempts and RBAC denials" | none
- evidence: `crates/kcc-web/src/authz.rs:165-180`. Each request checks only the session map and whether the role name still exists. The account's state is never re-read:
  ```rust
  let Some(session) = state.sessions().get(&id).await else { return Redirect::to("/ui/login")... };
  let (Some(username), Some(role)) = (
      session.username().map(str::to_owned),
      session.role().and_then(|signed_in| state.role(&signed_in.name)),
  ) else { ... };
  ```
  Only the Web admin handlers call `invalidate_user` (`session.rs:384-390`; `admin_users.rs:390,495,560`). The CLI path writes the store and nothing else (`crates/kcc/src/cli/accounts.rs:89-90`):
  ```rust
  UserCommand::Disable { username, enable } => {
      let found = accounts.administer(&username, &AccountChange::Disabled(!enable))?;
  ```
- impact: An operator runs `kcc user disable mallory` (or `kcc user passwd`) to lock out a compromised account. Mallory's open browser session keeps every Web permission. An active session refreshes its 30-minute idle deadline on each request, so it lasts until the 12-hour absolute timeout.
- fix: In `authentication_middleware`, check that the account still exists and is not disabled (a cached `AccountStore` generation or mtime check is enough). Alternatively, have `AccountStore::administer` and `change_password` publish a revocation that `SessionStore` consumes.
- confidence: high

### W1-02 Open SSE streams outlive logout, disable, delete and role reduction
- severity: medium
- kind: security
- rule: project rule (e) Web UI hardening; focus "SSE lifetime"
- evidence: `crates/kcc-web/src/overview.rs:135-151,172-174,222-226`. The role is captured once, the session is never checked again, and the stream has no lifetime cap:
  ```rust
  let Some(permit) = state.streams().try_acquire(&current.stream_key()) else { ... };
  let entries = match fleet.visible(user.role()).await { ... };
  ...
  let role = user.role().clone();
  ...
  Sse::new(held).keep_alive(KeepAlive::default())
  ```
  The other streams follow the same pattern (`dashboard.rs:202`, `net_interface_traffic.rs:58`, `system_pages/logs.rs:155`, `system_pages/jobs.rs:150`, `advanced/job_stream.rs:75`, `wizard/events.rs:131`). `SessionStore::invalidate*` only removes map entries (`session.rs:325-411`).
- impact: An admin disables a user, removes their router scope, or the user logs out. Fleet cards, traffic, router logs and explorer job output keep streaming on the already-open connection for as long as the browser keeps it. KeepAlive keeps it open, and the 12-hour absolute timeout is never applied to it.
- fix: In `guarded`, re-check the session every N events or every keep-alive tick with `sessions().peek(id)` plus the live role, and end the stream when the session is gone. Also cap a stream at the session's absolute deadline.
- confidence: high

### W1-03 Unauthenticated `GET /ui/login` grows the session map without bound
- severity: medium
- kind: security
- rule: RUST_GUIDELINES.md §10 "Validate and sanitize all external input at system boundaries"; focus "session store bounds"
- evidence: `crates/kcc-web/src/auth.rs:141-156`. A request without a cookie always inserts a new session:
  ```rust
  let existing = SessionStore::id_from_headers(&headers, state.cookie_security());
  ...
  let (id, anonymous) = match session {
      Some(value) => value,
      None => match state.sessions().create_anonymous().await {
  ```
  `session.rs:456-462` inserts with no cap. `session.rs:494-498` sweeps every entry under the single write lock. The default idle lifetime is 30 minutes (`kcc-app/src/settings.rs:158`). `login_page` also runs `has_admin` (`spawn_blocking` with a file read) per hit (`auth.rs:137`).
- impact: A client that sends `GET /ui/login` without cookies in a loop creates one entry of roughly 250 B per request, each kept for 30 minutes. At 1,000 requests per second that is about 1.8 million entries and hundreds of MB. Every authenticated request also takes the same write lock (`get` at `session.rs:297`), and the sweeper's `retain` over millions of entries stalls them.
- fix: Cap anonymous sessions, for example a separate bounded map or LRU of about 10k entries with a short lifetime of a few minutes. Alternatively, derive the pre-login CSRF token statelessly (an HMAC over a random nonce cookie) and create the server session only at login.
- confidence: high (INFERRED: exact memory per entry)

### W1-04 A failed sign-in shows nothing in the browser (401 is never swapped by htmx)
- severity: medium
- kind: bug
- rule: none (main-flow correctness)
- evidence: `crates/kcc-web/src/auth.rs:379-388` answers a failed login with 401:
  ```rust
  let mut response = (
      StatusCode::UNAUTHORIZED,
      errors::render(&LoginPage { ... error: tr(state.default_locale(), keys::ERRORS_AUTH_FAILED, None), ... }),
  )
  ```
  The form submits through htmx (`templates/pages/login.html`: `hx-post="/ui/login" hx-target="body"`). The vendored htmx 2.0.11 sets `responseHandling:[...,{code:"[45]..",swap:false,error:true}]`. `assets/js/app.js:27-32,418-424,450-456` override swapping only for 422, 413 and 403, and the refusal toast exists only on signed-in pages (`base.html`: `{%- if shell.signed_in() %}<template id="refused-toast">`).

- fix: Answer the failed login with 422, which app.js already swaps and which keeps the uniform text. Alternatively, add 401 to the app.js `beforeSwap` override.
- confidence: high

### W1-05 Editing a router seals the new secrets before the profile update, with no rollback
- severity: medium
- kind: bug
- rule: RUST_GUIDELINES.md §6 "`core::mem::DropGuard` for One-Off Cleanup and Rollback"
- evidence: `crates/kcc-web/src/routers.rs:236-250`:
  ```rust
  let mut profile = stored;
  fields.apply(&mut profile);
  if let Err(error) = plan
      .point(store, &mut profile)
      .and_then(|()| plan.seal(store, &id))
  { return errors::internal(&error, shell); }
  match fleet.registry().update(user.role(), profile.clone()).await {
      Ok(()) => {}
      Err(RegistryError::PermissionDenied { router: _ }) => { return errors::response(Kind::Forbidden, shell); }
      Err(error) => return errors::internal(&error, shell),
  }
  ```
  The sealed path is per id and kind (`plan.rs:182`), so `seal` overwrites the live `<id>.sealed` and `<id>.read.sealed` records in place. `create` rolls back on failure (`routers.rs:119-127`); `update` does not.
- impact: An edit changes the URL, login and password together, and `registry.update` then fails (I/O or lock error, or the role lost `ManageRouters` or its scope in between). The stored profile keeps the old URL and login but now decrypts to the new password. The poller and every write then fail to authenticate, and repeated bad logins may trip the router's own lockout (INFERRED). The read-only password breaks the same way.
- fix: Seal to the new records only after `registry.update` succeeds. Alternatively, snapshot the previous sealed bytes and restore them on any update error.
- confidence: high (INFERRED: router-side lockout)

### W1-08 Each audit-page view and export verifies and loads the whole log
- severity: medium
- kind: anti-pattern
- rule: overlay http-services "Every listener... DoS bounds"; RUST_GUIDELINES.md §4 "DON'T collect into Vec just to iterate again"

## Clean
- **CSRF middleware:** constant-time token compare, exactly one Origin checked against the allow-list, Fetch-Metadata check, and a session required for every non-safe method, login included.
- **Session ids and CSRF tokens:** 256-bit values from `SysRng`, with redacted Debug output.
- **Cookies:** `__Host-` prefix plus `Secure` under TLS, `HttpOnly`, `SameSite=Strict`, cleared on logout.
- **Session fixation:** the id rotates at login and at privilege change, and other sessions end after a password change.
- **CSP and headers:** CSP is `default-src 'none'` with only explicit `'self'` sources and no inline code. The kit default headers are kept. Assets are hash-addressed with SRI and an immutable cache policy, and unknown assets get the generic 404.
- **Route authorization:** the path-prefix permission table has defense in depth, because handlers re-authorize with the decoded router id (`fleet.visible`, `gate::allowed`, `context::managed`).
- **Role checks:** `dominates`/`covered` are conservative for `*`-only globs. Built-in roles cannot be edited or shadowed, nobody can act on their own account or role, and the last enabled admin is enforced by `AccountStore` under its file lock.
- **API key display-once:** the plaintext appears only in the create response, with `no-store`, hash-only storage, and no entry in the audit log (the test pins this).
- **Brackets:** the `own`/`hold`/`budget` claim state machine is race-free (compare-and-swap OPEN→HELD and OPEN→ENDED), and a panic is propagated rather than answered as 503.
- **Secret dialogs:** values come from the body only, mismatched entries are zeroized, nothing is echoed, query-string values are ignored, and both fields empty means "unchanged" (audited).
- **Templates:** askama auto-escaping throughout. `|safe` in scope is used only on nested askama templates, and the template lint rejects inline style or script and literal text.
- **Router form plan:** the endpoint-move rule (URL, login or TLS change needs the primary credential again and drops the read-only login), token and password mode switching, and the add-form rollback on a seal failure are correct.
