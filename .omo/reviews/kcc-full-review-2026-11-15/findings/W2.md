## W2 review report: page kit, table, wizard engine, system general page, config page

No critical or high findings. The worst issues are medium:
- confirmations are opt-in per page;
- wizard sessions can be evicted while a request still holds them;
- two audit gaps in the wizard finish.

### W2-01 Confirmation is opt-in, so management and destructive plans can run with no dialog
- severity: medium
- kind: security
- rule: project rule (e) and the kit contract (`page_kit.rs:13-17`: "management changes explain the fail-safe timer, destructive ones need the router name typed")
- evidence: `page_kit/submit/flow.rs:51-57`. Every submission starts with `ask: Ask::Never`. `submit.rs:317-321` only checks the planned risk if the page called `confirming_planned`:
  ```rust
  if let Some(resubmit) = course.planned()
      && let Some(prompt) = action.confirm(planned.risk, &params.confirmation(), resubmit)
  ```
  `net_wifi_settings.rs:231-241` submits with no `confirming*` call. The plan it builds is `wifi::plan_up`, and `kcc-domain/src/wifi.rs:166-172` gives that plan `Risk::Management` when the access point being disabled carries kcc's management path. `confirm/stakes.rs:41` says Management must ask (`Some(Guard::Management)`).

  A second gap: `flow.rs:59-62` lets `confirming(risk)` (`Ask::First`) replace `Ask::Planned`. If the plan then comes back at a higher risk, only the weaker confirmation was checked.
- impact: One click on "Disable" for the access point kcc reaches the router through runs a management change under the fail-safe timer, with no warning dialog. The same happens on any page that forgets the opt-in. The typed-name rule for destructive changes is enforced only where each page remembers to ask for it.
- fix: In `carry`, always run `action.confirm(planned.risk, …)` once the planned effective risk is Management or above. Make `Resubmit` a required argument of `Submission::new`, or derive it from the request URI. Keep `Ask::First` as an extra early check, not a replacement.
- confidence: high

### W2-02 Wizard session eviction breaks per-run mutual exclusion; any user with `Migrate` can trigger it
- severity: medium
- kind: bug
- rule: none (correctness)
- evidence: `wizard/visit.rs:54-59` creates the session before the record is loaded or its owner checked:
  ```rust
  let session = wizards.session(id);
  let turn = session.turn().await;
  let record = match services.store().load::<F>(id) {
  ```
  `wizard/service.rs:296-301` evicts any session whose `live` is `None`, even one whose `turn` is currently held:
  ```rust
  if sessions.len() >= KEPT
      && let Some(idle) = sessions.iter().position(|(_, session)| lock(&session.live).is_none())
  ```
  `migrate_wizard/launch.rs:52-85` holds the turn with `live == None` through `Prepared::new`, which reads the router, and only then calls `session.set_live`.
- impact: An operator who holds `Migrate` sends 64 GETs to `/ui/migrate/<valid-looking-id>`, which creates 64 sessions. Another user's run is evicted while its launch is in flight:
  - A second request on that run gets a fresh session and turn, so two requests interleave on the record.
  - The `Live` lands on the orphaned session. The page then reads the apply as interrupted (`resume.rs:311`), and finish answers 409 (`finish.rs:212-214`).
  - The verified changes can't be kept, and the router's timer rolls them back.
- fix: Load and check the record's owner before calling `wizards.session(id)`, then take the turn and re-read. Evict only sessions with `Arc::strong_count(session) == 1` and `live == None`.
- confidence: medium (INFERRED: the attack timing; the code path was read)

### W2-03 A wizard commit or rollback that succeeded on the router is not audited if the record save fails
- severity: medium
- kind: bug
- rule: project audit contract ("audit of every … failure")
- evidence: `wizard/finish.rs:243-251`:
  ```rust
  let done: Option<Applier> = slot.take();
  drop(slot);
  drop(done);
  end(state, wizards, &mut visit, (id, finished))?;

  ...

  ```
  `end` returns `Err(500)` when `visit.save()` fails (`finish.rs:275-280`).
- impact: If the disk is full or the state directory is unwritable, the router has already committed or rolled back, the user gets a 500, and `web.migrate_commit` / `web.preset_save` is never written. The audit log hides a completed router change.
- fix: Append the audit entry before `end`, or append it on the error path of `end` too.
- confidence: high

### W2-04 A rollback the router accepted is audited as a failure
- severity: medium
- kind: bug
- rule: brief focus ("audit … with the right outcome")
- evidence: `wizard/finish.rs:228-237`:
  ```rust
  if let Err(error) = result {
      ...
      let failed = Attempt::Failed { error: "router", fail_safe_armed: error.recovery_armed() };
      audit.append_attempt(state, user, failed).await;
      if error == ApplyError::RollbackRestarting {
          end(state, wizards, &mut visit, (id, F::ROLLBACK_RESTARTING))?;
  ```
  In kcc-migrate, `failure.rs:124` gives `RollbackRestarting` no armed fate, and `failure.rs:151` maps it to `MIGRATE_ROLLBACK_SAVED`.
- impact: On an extender whose reboot goes silent, the page reports the rollback as done (`MIGRATE_ROLLBACK_SAVED`). The audit log says `failed {error: router, fail_safe_armed: false}`. The forensic trail contradicts the UI. `silent_extender_*_rollback_reports_restarting` does not check the audit entry.
- fix: For `RollbackRestarting`, append the finish outcome (for example `restarting`, or `done` with the finish params) instead of a failed attempt.
- confidence: high

### W2-05 `Plan::at` drops the management bracket when the effective risk is Destructive
- severity: low
- kind: bug (latent)
- rule: project contract ("management changes always bracketed")
- evidence: `page_kit/change.rs:308-331`:
  ```rust
  /// Management recovery remains required when a destructive sibling raises risk.
  management: bool,
  ...
  pub(crate) const fn at(mut self, risk: Risk) -> Self {
      self.management = matches!(risk, Risk::Management);
  ```
  `apply` (`change.rs:341-370`) restores the flag only for `RawRci` Batch, Cli and Delete changes. `Change::Request` is always `false`. `Planned::of` takes the maximum risk (`work.rs:79-85`), and `Risk` orders `Management < Destructive`.
- impact: A curated plan that combines a management op with a destructive op runs without the fail-safe timer. The field's doc claims the opposite. No current page combines the two (INFERRED from the grep of `Planned::` callers).
- fix: Carry "contains management" separately in `Planned`, using the max-risk op set plus an OR of management. Set `Plan::at` from `risk == Management || planned.management`.
- confidence: medium

### W2-06 The config page's backup "copy" logic is built on a false premise
- severity: low
- kind: anti-pattern
- rule: §11 "no defensive checks in trusted code", plus the brief's dead/duplicated logic
- evidence: `config_page/store.rs:122-124`:
  ```rust
  /// Serializes the backups the page stores: the store names a backup by its second and
  /// reason, so a second one in the same second would replace the first.
  static STORING: Mutex<()> = Mutex::new(());
  ```
  The store never replaces a backup. `kcc-app/src/backups/store.rs:86-108` writes with `write_exclusive` and loops over a `{created_at}-{sequence}-{reason}` suffix. The page's `keep` (`store.rs:264-285`) still:
  - probes each candidate by decrypting it with `store.get`;
  - takes the second from `SystemTime::now()` rather than the store's clock;
  - holds a process-global lock across all routers.
- impact:
  - Extra decryptions on every create and upload.
  - Backup creation is serialized across routers.
  - A 10th upload in one second is refused as `taken` although the store would keep it.
  - `--N` reason mangling, with parsing in `backup_rows.rs:361-365`.
  - `COPIES`, `COPY_MARK`, `REASON_ROOM` and `StoreError::Taken` exist only to support this.
- fix: Call `store.create` directly. Delete `STORING`, the copy loop and `Taken`, and drop the `--N` handling.
- confidence: high

### W2-07 Read-only page views do far more work than needed
- severity: low
- kind: anti-pattern (performance/DoS)
- rule: §4 "DON'T: Clone gratuitously / allocations"; §5 "yield in CPU-bound async"
- evidence:
  - `config_page/store.rs:233-241` decrypts each shown backup just to show its size (`let text = store.get(&id, &name).ok()?; … text.expose_secret().len()`). It is called for every page GET and every refresh (`backups.rs:110-114`).
  - `table/rows.rs:115-116` sorts with `left.key(..).cmp(&right.key(..))`, and `SortKey::text` allocates a lowercase copy on every comparison.
  - `config_page/compare.rs:185-187` runs a Myers diff of up to 1,000 edits on the async worker.
- impact: Any user with Read can make the server decrypt up to 50 backups of up to 1 MiB each per page load. Large tables sort with O(n log n) allocations.
- fix: Take the size from file metadata (or record it in `BackupInfo`). Use `sort_by_cached_key`. Run the diff in `spawn_blocking`.
- confidence: high

### W2-08 The wizard store does blocking file I/O, including fsync, in async handlers
- severity: low
- kind: guideline
- rule: RUST_GUIDELINES.md §5 "DON'T: Call blocking I/O in async functions" (line 1112)
- evidence: `wizard/store.rs:648-652` calls `options.open(&temporary)?; file.write_all(bytes)?; file.sync_all()?; … fs::rename(..)` directly from async code: `visit.rs:59`, `visit.rs:105` (`save`), `finish.rs:275`, `settle.rs:506`, and the SSE closure in `events.rs:136-141`. The config page's store wraps the same kind of work in `spawn_blocking` (`config_page/store.rs:172-181`).
- impact: Each wizard step parks a tokio worker on fsync. The two stores are inconsistent with each other.
- fix: Wrap the `Store` calls in `spawn_blocking`, the way `config_page::store::blocking` does.
- confidence: high

### W2-09 Save does not re-check the "not while the timer is armed" rule the page shows
- severity: low
- kind: bug
- rule: kit contract (`gate.rs:4-5`: "a hidden button is not a permission check")
- evidence: `partials/config_status.html:19` shows Save only when `may_save() && state.unsaved() && !state.armed()`. `config_page/safety.rs:66-80` runs `configuration::save` without the `while_armed` check (in the opposite sense) that commit and rollback use.
- impact: A direct POST to `/config/save` while the fail-safe timer is armed saves the guarded changes but leaves the timer armed. The router then reboots when the timer fires, whereas Keep changes would have disarmed it (INFERRED: router-side behaviour).
- fix: Refuse Save while `fail_safe.active` is true, audited as `armed`, mirroring `while_armed`.
- confidence: medium

## Clean
- `Operation::open` checks the router and its scope, then the descriptor's permission, before any router request, and audits `forbidden`. `Action::plan` re-checks at the effective risk.
- The change pipeline holds every write with `brackets::hold()` before the first change, runs management changes through `guarded` with the change's own permission, and audits `ModeUnknown` and unowned refusals.
- The typed-name gate can't be bypassed: `Guard::check` needs `confirm=yes` and the exact name, which the server checks on every request. `TypedNameForm` rejects unknown fields.
- Sort and page parameters are validated: the column comes from a static allowlist, the direction from a parsed enum, and the page is clamped. The pager and filter links use `form_urlencoded`.
- Wizard ids pass `is_id` before every path join that matters, run files are written 0700/0600 via a temp file and rename, and sealed parts are bound to their owner (covered by a test).
- The finish permissions (Migrate+Destructive for rollback, per-wizard keep sets) are re-checked in `finish` before the applier runs.
- The redacted download masks every `ns3` blob and registered secret, drops the checksum and marks the copy; the full download needs `RevealSecrets`; both are audited with the variant only.
- Raw restore needs Destructive+Migrate, refuses another model or unknown firmware before asking, and requires the typed name.
- Upload: the 1 MiB limit is enforced, the file must be text and a parseable configuration, a redacted copy is refused, and the file name is reduced to a safe reason.
- The diff edit script is bounded by `MAX_EDITS` and falls back to a multiset comparison. Secrets are replaced before display; the hashes used for comparison never reach the page.
- `system_general` inputs are checked against strict charsets before planning, and the factory reset re-checks the typed name in the domain.
- `audit::field_names` and the masking of secret fields keep values out of audit entries, as the tests check.
