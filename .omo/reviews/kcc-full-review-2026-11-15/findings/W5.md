# Lane W5 review: migrate_wizard, presets_page, dashboard/fleet/telemetry

### W5-01 An abandoned or timed-out Apply leaves the router claimed for the rest of the process's life
- severity: medium
- kind: bug
- rule: RUST_GUIDELINES.md §5 "Annotate every async fn with cancel safety" (1188), §6 "RAII Guards" (1290)
- evidence: `crates/kcc-web/src/migrate_wizard/apply.rs:75-88`
  ```rust
  if !wizards.claim(&target, &id) { ... }
  match launch(&mut visit, &state, &jobs, &wizards).await {
      Ok((job, commands)) => { ... }
      Err(failure) => {
          wizards.release(&target, &id);
  ```
  `brackets.rs:142-150`: `budget` drops the handler future after `REQUEST_TIMEOUT` (30 s) unless `hold()` was called. `own`/`Abandon` aborts it when the client goes away. Neither apply handler calls `brackets::hold()`. `launch` first does the router reads in `Prepared::new` (`migrate_wizard/launch.rs:53`) or `Basis::of` (`presets_page/launch.rs:60`), then `Applier::start(...).await`. The same claim-then-await pattern is at `presets_page/apply.rs:87-100`.
- impact: A user confirms Apply, and either the fresh read of a slow target takes more than 30 s or the user closes the tab. The future is dropped at an `.await`, so `release` never runs. The `active` entry (`wizard/service.rs:52-57`) keeps the target. Every other run of that wizard against that router then gets "busy" until kcc restarts. A related path: if `visit.save()` fails at `launch.rs:109` after the job started, `apply.rs:88` releases the claim while the job is running, and the record has no `run`, so the user cannot follow, commit or roll back.
- fix: Wrap the claim in a guard whose `Drop` releases it unless it is disarmed after `start_run` has been saved. Do the reads before claiming, and call `brackets::hold()` right before `Applier::start`.
- confidence: high for the claim leak (INFERRED: how often a real target read takes more than 30 s).

### W5-02 Fleet and dashboard SSE streams keep running after logout, user disable or role change
- severity: medium
- kind: security
- rule: overlay http-services (control weakening); project rule (e)
- evidence: `crates/kcc-web/src/overview.rs:466-497` captures `let role = user.role().clone();` once per stream. `overview.rs:514-526` `guarded` only holds the permit. `dashboard.rs:217-224` captures the role into `LiveContext`. `session.rs:384-410` `invalidate_user` / `invalidate_role` only remove entries from the session map:
  ```rust
  pub(crate) async fn invalidate_role(&self, name: &str) {
      self.inner.sessions.write().await
          .retain(|_id, session| session.role.as_ref().is_none_or(|role| role.name != name));
  ```
- impact: An admin narrows a role's router scope or disables a user. That user's open `/ui/sse/fleet` and `/ui/sse/r/{router}/traffic` streams keep pushing cards, live regions and traffic for routers no longer in scope, with no time limit.
- fix: Pass the session id and the store into `guarded`, and end the stream when `peek(id)` returns `None`. Check it on each event and on the keep-alive tick, or cap stream lifetime at the session idle timeout.
- confidence: high

### W5-03 Migrations keep the whole sealed source config and the typed passwords forever
- severity: medium
- kind: security
- rule: project rule (i) "retention limits apply to ... backups"; project rule (d)
- evidence: `migrate_wizard/finish.rs:21-64` does not override `discard`. The default is a no-op (`wizard/finishing.rs:86-87`):
  ```rust
  fn discard(_services: Services<'_>, _id: &str) {}
  ```
  Presets do override it (`presets_page/finish.rs:69-71`). A restore copies the backup into the run (`migrate_wizard/landing.rs:212-216`, `store.seal(... Sealed::Source, text)`). No code deletes `<state>/migrations/<id>/`. Grepping for `discard(`/`remove_dir` finds only the preset paths. Copy runs expire only lazily: `saved::sweep` is called only from `/ui/copy` (`presets_page/landing.rs:81,151`), and `access.rs:59-67` opens the transient preset without checking its age.
- impact: Every migration ever started, including ones abandoned at step 1, keeps `source.sealed` (the full startup-config with every secret) and `passwords.sealed` on disk. That outlives backup retention and backup deletion. A copy run older than 24 h still works until someone opens `/ui/copy`.
- fix: Override `Finishing::discard` for the migration record (remove `Source` and `Passwords`). Check the age in `PresetRun::preset` for `Origin::Copy`. Add a retention sweep for run directories.
- confidence: high

### W5-05 Wizard file I/O, including fsync, runs on the async workers
- severity: medium
- kind: guideline
- rule: RUST_GUIDELINES.md §5 "DON'T: Call blocking I/O in async functions" (1112)
- evidence: `wizard/store.rs:324-328`:
  ```rust
  let mut file = options.open(&temporary)?;
  file.write_all(bytes)?;
  file.sync_all()?;
  drop(file);
  fs::rename(&temporary, directory.join(name))?;
  ```
  It is reached synchronously from async handlers. For example, `migrate_wizard/inputs_submit.rs:85-96` does a seal, then save, then save again. `Store::list` (`store.rs:141-169`) reads every run of every user from `landing.rs:136`. `wizard/events.rs:305-310` does `store.load` inside the stream. The crate already uses `spawn_blocking` for the registry (`fleet.rs:196-197`).
- impact: On slow disks every wizard click blocks a tokio worker for one or more fsyncs. Listing gets slower as runs pile up (see W5-06), which stalls unrelated requests and SSE streams on that worker.
- fix: Make the `Store` methods async over `spawn_blocking`, or wrap them in a `spawn_blocking` helper.
- confidence: high

### W5-11 A user-controlled form size makes review submit quadratic on the async worker
- severity: low
- kind: security
- rule: BRIEF "DoS bounds"
- evidence: `migrate_wizard/review_submit.rs:138-144` loops over every posted `shown` index and calls `last(form, &field)`, which is a linear reverse scan (`page_kit/request.rs:69-75`). `count` comes from the user's own uploaded source, up to 1 MiB of config. ### W5-12 Up to 64 sessions are shared by all users; eviction drops a session another request is still using
