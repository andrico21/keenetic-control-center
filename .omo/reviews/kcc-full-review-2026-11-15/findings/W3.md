I reviewed lane W3 read-only, as the brief requires. I didn't run cargo or any tests. I found 0 critical, 0 high, 6 medium, 10 low and 1 info findings. The main one: several handlers send a management change without asking the user first, and the tests hide this because they post `confirm=yes` up front.

### W3-01 Management-risk changes run without the fail-safe confirmation on several handlers
- severity: medium
- kind: security
- rule: overlay keenetic-control-center.md, Safety model: "Changes that can cut kcc off … run under the router's fail-safe timer". The kit's own `Stakes::guard` puts `Risk::Management` under `Guard::Management`.
- evidence: `page_kit/submit/flow.rs:51-56` makes `Ask::Never` the default:
  ```rust
  pub(super) const fn new() -> Self {
      Self { ask: Ask::Never, landing: Landing::Own, refresh_failed: false }
  ```
  These handlers get their risk from planners that can classify a change as management, but none of them calls `.confirming_planned(..)`:
  - `net_wifi_settings.rs:231-245`. `wifi::plan_up(.., false)` uses `detect_management`.
  - `net_internet_order.rs:62-72` (default route) and `:101-128` (order). `wan::plan_priority` uses `classify_generated`.
  - `net_internet_edit.rs:270-284` (priority). `net_internet_create.rs:277-285` (`wan::plan_create`, classified). `net_internet_delete.rs:101-115` (`wan::plan_delete`, classified, `kcc-domain/src/wan.rs:111-120,289-306`).
  - `clients_pages/segment_create.rs:73-110`. The wizard's Create button sends no confirmation field (`segments_review.html:17`).

  Compare `net_internet_address.rs:193`, `.confirming_planned(resubmit)`, and `firewall_page/run.rs:133`.
- impact: An operator clicks Disable on the access point kcc is connected through (`net_wifi_tables.rs:119-127`, `Act::sends`). The page posts at once and the change runs inside the fail-safe bracket, with no "this can cut kcc off" dialog. The same happens for Move up/down on the WAN that carries kcc and for creating a segment that moves kcc's access point. The control is enforced only by the pages that remember to opt in.
- fix: Make `Course::new()` default to asking at the planned risk (`Ask::Planned`), with an explicit opt-out for pages that confirm on their own. Otherwise, add `.confirming_planned(resubmit)` to each handler listed above.
- confidence: high

### W3-02 Firewall pages require `Destructive` for management changes; every other page requires only the change's permission
- severity: medium
- kind: bug
- rule: brief, owner decision "operators may apply (the recovery timer runs under the protected change's permission)"; RUST_GUIDELINES §7 (duplicated policy logic).
- evidence: `firewall_page/run.rs:154-158`:
  ```rust
  let risk = interfaces_risk(domain, &interfaces).await;
  let needed = [Permission::Write, Permission::Destructive];
  if risk >= Risk::Management && !allowed(self.user, self.router, &needed) {
      return Err(DomainError::PermissionDenied);
  ```
  The kit's rule is different: `kcc-domain/src/configuration.rs:223-228` adds `Destructive` only for `risk >= Destructive`. Tests pin both behaviours: operator/writer get 403 in `tests/routing_pages/firewall_bind.rs:59-70`, but are allowed in `tests/network_pages/wifi.rs:104-114` and `tests/clients_pages/segments.rs:110-129`.
- impact: An operator may take an access point down, or move it into a new segment, under the timer. The same operator gets 403 when applying an access list to `Bridge0`. That is one policy decided in two places, and they disagree.
- fix: Delete the hand-written check and let `Action::run_planned` → `Action::plan` (`SafetyNet::required`) decide. If firewall really needs `Destructive`, express that in the firewall descriptor's risk.
- confidence: high

### W3-03 Wi-Fi SSID, security, channel and country changes are never management-classified, but disabling the same access point is
- severity: medium
- kind: security
- rule: project overlay Safety model (management changes run under fail-safe); focus item "correct planner called with correct risk".
- evidence: `kcc-domain/src/wifi.rs:166-173` classifies only the disable:
  ```rust
  let risk = if enabled { Risk::Write } else {
      interfaces::detect_management(router, name).await?.risk(name) };
  ```
  `plan_ssid`/`plan_encryption` (`wifi.rs:129-151`) and `plan_channel`/`plan_country_code` (`:208,241`) go through `plan::plan`, a plain write. The web passes them straight through (`net_wifi_fields.rs:285-298`, `net_wifi_edit.rs:92-96`).
- impact: kcc's host is on `WifiMaster0/AccessPoint0`, which the fake router classifies as management (see the `wifi.rs` test). Changing that access point's SSID or security to WPA3 drops kcc's link. No fail-safe timer is armed, so nothing rolls back.
- fix: Classify these planners with `detect_management` the same way `plan_up(false)` does. Then use `confirming_planned` on the `net_wifi_edit::field` POST (see W3-01).
- confidence: medium (INFERRED: kcc reaching the router over Wi-Fi in real deployments; the code path is verified)

### W3-05 Failed router reads are swallowed into defaults that drive later changes

## Clean
- **Authz and router scope:** every change handler opens an `Operation` (scope plus permission re-check plus audit) before reading the form. Read-only dialogs and the SSE stream go through `context::target`.
- **Secrets:** PPP passwords and Wi-Fi PSKs are only ever shown as "Set"/"Not set". No secret value is rendered, put into a resubmit URL, or audited (only field names in params).
- **Object names:** names travel in the query or form, are parsed as `ObjectName` at the boundary, and never reach an RCI path. The drawer test checks this.
- **Free-text fields:** descriptions, client names and policy words reject control characters, quotes and spaces before they reach a CLI line.
- **Pagination:** NAT sessions cap the page (`LAST_PAGE`) and the filter length. `Pager` clamps the page. Sort columns are whitelisted by `Row::COLUMNS`.
- **Typed-name deletes:** WAN, policy and segment deletes compare `object` with `confirm_name` on the server. Segment delete also checks a summary fingerprint against a fresh read.
- **Firewall and NAT rule actions:** they act only when a fresh read still has the named rule at that position (`Named::find`, `forwards(&known).contains(..)`).
- **Route wipe:** the route-wipe guard reports and audits restored or missing routes (scope already in BACKLOG).
- **Module size:** every module in scope is under 310 lines. I found no `#[allow]` and no review-process labels.
