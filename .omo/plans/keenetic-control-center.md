## TL;DR (For humans)

<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**Who this is for and what changes for them:** Owners of Keenetic and Netcraze routers (firmware 4.3 LTS and newer) get one place, mainly a web page in their own language, to see and change every setting of all their routers, keep backups, and move all settings from an old router to a new one safely. AI assistants and scripts get the same powers through an MCP server and a command-line tool.

**What you'll get:** A single program (`kcc`) for Linux, macOS, Windows and Docker that serves a six-language web control center (English, Russian, Ukrainian, German, Belarusian, Kazakh) with logins and roles, a fleet dashboard, pages for all everyday router areas, a command explorer that reaches every documented router command, backups with diffs, and a step-by-step migration wizard. The same engine also powers an MCP server for AI agents and a scriptable CLI, exports router and app metrics to Prometheus (with a ready Grafana dashboard and alerts), forwards router logs to Loki or Elasticsearch/OpenSearch, refuses to run with root/sudo or extra privileges, saves reusable settings presets (DoH/DoT, DNS, routing, firewall, VPN clients, Wi-Fi, baseline, users, schedules) captured from one router and applied to another, and ships as a hardened image for rootless Podman with its own seccomp profile.

**Why this approach:** The router's official API mirrors its command-line reference one-to-one but cannot describe itself, so we turn the official per-model reference manuals into a built-in command catalog and check every request against it. This gives full coverage and stops the router's worst habit: silently ignoring a misspelled setting. Every change is read back, nothing is saved without your say-so, and risky changes and migrations run under the router's own auto-rollback timer, so a mistake that cuts you off undoes itself.

**What it will NOT do:** It will not modify firmware, install anything on the router, or use Keenetic's cloud. It will not save router changes on its own or skip certificate checks. It will not migrate things tied to the old device (KeenDNS registration, certificates, MAC addresses, LED/USB hardware settings); those are listed in the plan with the reason.

**Effort:** XL
**Risk:** Medium - Several router behaviours rest on one source each: replaying settings one line at a time, admin password hashes being tied to the model name, the fail-safe timer's exact behaviour, and whether the manuals can be turned into data reliably. Two early experiments and a pass/fail check on the catalog settle these first, each with a fallback agreed in advance.
**Decisions to sanity-check:**
- Admin/user passwords are re-entered during migration instead of copied.
- In a full migration, Wi-Fi/PPP passwords and WireGuard keys are copied as-is (the new router replaces the old one); presets instead regenerate WireGuard keys by default.
- The command catalog stores only command structure, with page links to Keenetic's PDFs and none of their text (the manuals are copyrighted and carry no license).
- AI agents see a small core set of at most 25 tools by default; more sets are switched on in config.
- Live tests only touch routers whose serial numbers you list.
- Migration and presets only go onto the same or newer firmware than the source, and expect a clean new router (a non-clean one only gets a warning).
- Presets copy settings groups one source -> one target per run; WireGuard keys are regenerated on the target by default (you register the new public key on your VPN server).
- Firmware 4.3 LTS and 5.0 are supported from the official manuals and tested only against the simulator (your hardware runs 5.1+); kcc labels them "not verified on real hardware" and asks for confirmation before migrating onto them.
- Router logs are pulled through the router API (no syslog listener); anything still buffered when kcc stops, or beyond a 10 000-line buffer while a log server is down, is lost and counted.
- Root, `sudo` and Windows elevation are refused with no override flag, as in krb-passwd-ui.
- Metrics are served on a separate, unauthenticated, loopback-only listener (how rmcp-server-kit does it); per-device metrics are off by default.
- Router passwords are stored encrypted in the app's state folder (no OS keychain).
- Web login uses local accounts, with OIDC possible later.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- No `unsafe` (`unsafe_code = "forbid"`), no `#[allow]`, no manifest-level allows beyond the profile's `redundant_pub_crate`, no `unwrap`/`expect`/`panic!` in non-test code, no `println!`/`eprintln!`/`dbg!`.
- No XML `/ci` API (deprecated), no Keenetic Cloud/RMM integration, no firmware modification, no on-router (Entware) build, no OS keychain integration, no TUI.
- No skipping TLS verification for routers (verify or SHA-256 pin only); no following HTTP redirects to routers.
- No automatic `system configuration save` after a change unless the caller explicitly asks; MCP never saves on its own.
- No raw tool/form input interpolated into RCI paths or CLI lines without catalog validation and identifier validation.
- No npm/Node toolchain in the build; no CDN assets; no inline `<script>`/`style=` attributes; no `hx-on` (needs eval).
- No committing downloaded vendor PDFs or any manual prose (the catalog stores facts only: paths, arguments, types, ranges, flags, since-version, page number, source URL + sha256); no real router secrets/MACs/IPs in fixtures.
- No stored client telemetry/presence history (live charts are in-memory ring buffers only).
- No silent acceptance of a router's user agreement (DPN/EULA): the operator confirms the router's own text, and it is audited.
- No pushes to external repositories (e.g. the rust-guidelines overlay PR) without explicit owner approval; no git commits unless the owner requested them in the execution session.
- No live write tests unless `KCC_LIVE_ALLOW_WRITE=1` and the router profile is marked `test_device = true`.
- No override flag for the privilege floor ("prohibited, no excuses"); no `std::process::Command` in product crates.
- No multi-target or fleet-wide preset apply (owner chose one-to-one), no preset export/import files, no preset editor beyond per-item include/exclude at apply time; no migration or preset apply onto older firmware than the source.
- No syslog listener, no disk spool for log forwarding, no OpenTelemetry/Influx exporters, no Kubernetes manifests (not requested); no per-client metric series unless enabled.
- The metrics listener never binds a non-loopback address by default (it is unauthenticated, R-KIT GUIDE metrics section).

## Verification strategy

- Test decision: **tests written in the same todo as the code** (tests-after within the todo); auth/crypto known-answer vectors and parsers are test-first. Frameworks: built-in `#[test]`/`#[tokio::test]`, `proptest` (parsers, validators, codecs, MCP argument fuzzing), `cargo nextest` profiles (`.config/nextest.toml`), the `kcc-testkit` axum fake router for integration, env-gated live suites, Playwright MCP (agent-driven browser) for UI QA in F3.
