# kcc-notify-schedule - Work Plan

## TL;DR (For humans)
**Who this is for and what changes for them:** You, running `kcc serve` for your household's routers. Today you only learn that something went wrong by opening the Web UI, and kcc can do nothing at a set time. Afterwards kcc sends you short Telegram messages when something needs your attention, and it carries out a few chosen actions on a weekly timetable: switching a device's connection policy, applying a saved preset, making a backup, or restarting a router.

**What you'll get:**
- Telegram set up on a Web admin page (or the command line): paste the bot token once, add one or more chats, pick which events you want and the language. A "send test message" button proves it works.
- Messages for: a router going offline or coming back, a router refusing kcc's login, a change that failed (and whether the router's safety timer will undo it), a scheduled action that failed or was skipped, an account locked after wrong passwords, an audit-log repair, new router firmware (once per version), and failed background jobs. "New unknown device" exists but is off by default. Device names and addresses stay out of messages unless you switch that on.
- A "Scheduled actions" admin page and `kcc scheduled` commands: pick the days, the hour and minute, the time zone, and one of the four actions. Each run is checked against the permissions its owner holds at that moment and goes through kcc's normal safety steps; scheduled changes are never saved to the router's startup settings, so a router restart undoes them, and every message and the configuration page say so.
- The router dashboard shows the next scheduled action, and each router's configuration page names a scheduled run whose changes are still unsaved.

**Why this approach:**
- Telegram is one-way (kcc only sends) and its address is fixed in the server's configuration file, so nobody using the Web UI can redirect the bot token elsewhere.
- Schedules run only inside `kcc serve`, at most once per time slot, and a run that is more than two minutes late is skipped and reported rather than run at a surprising time. Time zones and daylight-saving changes are handled by a well-tested time library with its own copy of the world time-zone data, so the container and the release builds behave the same.

**What it will NOT do:**
- No commands sent to kcc through Telegram, no other messaging services, and nothing new for AI assistants.
- No automatic saving, no "catch up" of missed runs, no scheduled permit/deny of a device (the router already schedules that itself), and no cron-style expressions.
- No stored history of devices: "new device" detection lives in memory only.

**Effort:** XL
**Risk:** Medium - a new dependency (the time library) and a new outbound destination plus unattended router changes, mitigated by run-time permission checks, the normal change workflow, never saving, and tests against a simulated router and a simulated Telegram.
**Decisions to sanity-check:**
- Successful scheduled runs are not messaged by default (failures and skips are); you can switch successes on.
- A scheduled preset needs the same permissions as applying it by hand (Read, Migrate, Write, Save); if it fails, kcc rolls it back itself, which the existing code allows under Migrate.
- Telegram's server address can only be changed in the configuration file; the Web page edits everything else.
- kcc polls every router around the clock while notifications are on, so it can notice outages.
- Scheduled access permit/deny is left out because routers schedule that themselves.

Your next move: start execution with `$ulw-execute kcc-notify-schedule` once CI is green on `master`. Full execution detail follows below.
