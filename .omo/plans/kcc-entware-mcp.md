# kcc-entware-mcp - Work Plan

## TL;DR (For humans)
**Who this is for and what changes for them:** You, managing your Keenetic and Netcraze routers from kcc, and the AI assistants you connect to kcc. Two things change. First, kcc gains Entware support: it shows whether Entware can run on a router, sets it up, changes its settings and, for routers you opt in, installs packages and starts services over a locked-down SSH connection. Second, MCP, the channel AI assistants use, becomes manageable on the Web UI: its settings, an optional port of its own, and four ways to sign in. API keys stay. New are logging in with your kcc account in the browser, your own identity provider such as Keycloak, and client certificates.

**What you'll get:**
- Everything from the approved Entware plan: an Entware status view, a guided setup, settings with warnings, drive preparation, and opt-in package and service management over SSH that only ever runs a fixed set of commands.
- An MCP page under Administration, for admins only:
  - Every MCP switch: the toolsets on offer, read-only mode, destructive tools, the result size limit and the local stdio mode.
  - An optional MCP-only port.
  - The sign-in methods for each port.
  - Your kcc.toml values act as defaults. Keys you lock in kcc.toml, or set through environment variables, show as read-only.
  - Changes that make kcc less safe ask for your password again and are logged.
  - Changes take effect immediately. Where the underlying server needs a restart, kcc restarts it inside the running process, checks it came back healthy and reverts automatically if not.
- API keys with an optional expiry date.
- "Sign in with kcc" for MCP clients such as Claude Code, Codex, Cursor and VS Code. The client opens your browser, you log in with your kcc account and approve on a translated consent page, and the client gets a short-lived token tied to your account. When you disable the account, change its role, change its password or revoke the connection on the new "MCP connections" page, it stops working at the next request.
- Tokens from your own identity provider (Keycloak, Authentik and similar), with their groups or roles mapped to kcc roles.
- Client-certificate sign-in for scripts and custom agents: you upload your certificate authority on the Web page.

**Why this approach:**
- The MCP server library kcc uses (rmcp-server-kit) already checks certificates and identity-provider tokens. kcc turns those on and adds the parts the library lacks: issuing its own tokens from your kcc accounts, the consent page, and restarting the listener safely.
- Each kcc token is re-checked against your account on every request, so revoking access never waits for the token to expire.

**What it will NOT do:**
- No MCP without sign-in over the network, no way for an AI assistant to change MCP or sign-in settings, and no file paths typed into the Web page.
- No sign-in through the library's built-in proxy for now: its consent page is English-only, so it waits until the library can show a translated page.
- Everything the Entware plan excluded still holds: no free shell, no stored Entware password, no automatic saving.

**Effort:** XL
**Risk:** High - two new trust boundaries (SSH to Entware; kcc as a sign-in server) and in-process restarts of the server that also hosts the Web UI. They are mitigated by pinned SSH host keys, per-request account checks, an automatic health check and revert after every restart, and a test for each failure path.
**Decisions to sanity-check:**
- Restarting the main server live was your choice. A failed restart reverts automatically, but open MCP sessions on that port drop during a restart.
- The library's OpenID signing dependency pulls in an RSA crate with a known timing advisory (RUSTSEC-2023-0071). It is ignored with a reason until you release rmcp-server-kit with jsonwebtoken 12, because kcc only ever verifies RSA signatures.
- "Sign in with kcc" needs kcc to be reached under a DNS name or on localhost: the library refuses an IP address as the sign-in server's name.
- Almost no desktop MCP client presents client certificates today, so certificate sign-in mainly serves scripts and custom agents.
- Every SSH action needs the Destructive permission (carried over from the Entware plan).

Your next move: start execution with `$ulw-execute kcc-entware-mcp`. CI on `master` must be green. This plan replaces `kcc-entware`, so never run `$ulw-execute kcc-entware`. Full execution detail follows below.

## Scope
### Affected user and ideal state
**Affected user:**
- **U1 router owner/admin** (Web UI main, CLI): today cannot see or manage Entware from kcc; uses the router UI and an SSH client by hand; manages MCP only by editing kcc.toml and restarting, with API keys as the only sign-in. After: sees status, sets Entware up end to end, changes settings, and (opt-in) manages packages and services from kcc; administers MCP on the Web (settings, dedicated listener, sign-in methods, connections) and signs MCP clients in with the kcc account.
- **U2 AI assistant over MCP** (possibly prompt-injected) and the MCP client it runs in (Claude Code, Codex, Cursor, VS Code, MCP Inspector, scripts): today has no Entware tools and signs in only with an API key. After: gets Entware tools only in toolsets the owner enables; every SSH tool needs `allow_destructive` and `confirm: true`; it never sees a password, a private key or raw SSH output; it can sign in through OAuth with a kcc account, an IdP token or a client certificate, and can never change MCP or sign-in settings.
- **U3 operator of `kcc serve`/the container**: after: a new outbound SSH path that obeys the outbound policy, the seccomp profile and the CI gates; an optional second published port for MCP; kcc.toml keys can be locked against Web edits; the kit's `oauth` feature with a documented advisory ignore.
- **U4 household members**: after: DNS override and removing or wiping the Entware drive never happen without a warning naming the effect; migrations no longer copy Entware DNS settings to routers without Entware.
- **U5 maintainers/the worker**: everything testable without hardware; the owner runs live suites later.

  - **Chroot:** `opkg chroot` makes init scripts run with root `/opt` (manual 3.139), so kcc's absolute paths would not exist in SSH sessions. Every flow that opens an SSH connection (probe, bootstrap, re-pin, revoke and every operation) reads `opkg chroot` over RCI first and refuses with `EntwareError::ChrootEnabled` while it is on; local-only flows (`disable`, `set_enabled`, `set_port`) never contact the router; enabling chroot warns that SSH management stops working.
  - **SSH:** default port 222 (Keenetic docs: 222 when the router's SSH server component is installed, else 22), configurable per router 1..=65535; connect 5 s, auth 10 s, read commands 30 s, mutations 600 s (all injectable through a `Timeouts` value for tests); at most one session per router and 4 in total; 256 KiB output cap per command (abort, report truncated); keepalive 15 s; inactivity timeout 60 s; preferred host-key algorithms `ssh-ed25519` only.
  - **Service actions follow Entware `rc.func`** (https://raw.githubusercontent.com/Entware/rtndev/master/entware-opt/files/rc.func): actions `start|stop|restart|check|kill|reconfigure`; any other prints usage and exits 1. kcc's "status" uses `check`: exit 0 with `alive.` in the output -> Running, exit 1 with `dead.` -> Stopped (match the words as substrings; rc.func wraps them in ANSI colour codes). Action exit codes: `start` 0 ok (also when already running), 8 `ServiceDisabled` (`ENABLED` is not `yes`), 255 failed; `stop` (= `check && stop`) 0 ok, 1 already stopped (ok); `restart` (= `check >/dev/null && stop; start`) 0 ok, 8 `ServiceDisabled` (the service is now stopped; report it), 255 failed; anything else `UnexpectedOutput`. After every action the `check` read-back decides the outcome.
  - **SSH state** for both profile sources lives in the state directory under `<state>/router-ssh/` and is NOT a `CredentialKind` (the router credential flows - `credential_path`, plaintext migration, edit rollback - stay untouched): private key `<id>.key.sealed` (AD `router:<id>:ssh-key`, OpenSSH private text as `SecretString`); enrolment record `<id>.sealed` (AD `router:<id>:ssh-state`) holding `{enabled, port, state: pending|active, router_host, host_key (OpenSSH public line), fingerprint (SHA256:base64), enrolled_at, enrolled_by}`; probe tickets `<id>.ticket.sealed` (AD `router:<id>:ssh-ticket`), single-use (consumed atomically by rename-then-read), 5-minute expiry, bound to router id, port and actor. Every use compares `router_host` with the router's current URL host; on a difference the record becomes `Pending` with the pin cleared and operations are refused until a new probe and bootstrap (covers both `kcc.toml` and stored routers without registry hooks). Router removal calls `entware_ssh::forget(state, id)`.
  - **Service log** = router `show log` records (parsed with `parse_records_now`) whose `process` equals the service's base name (`S51dropbear` -> `dropbear`), read over RCI in kcc-domain and passed through the shared masker unless the principal holds `RevealSecrets`; no file is read over SSH.

## Execution strategy
### Parallel execution waves
> Target 5-8 todos per wave. Fewer than 3 (except the final) means you under-split.

Todo numbers are identifiers, not order; execute by the dependency matrix. Parallel todos run in separate worktrees with at most 2 concurrent cargo builds. Two dependency intakes (todos 6 and 29) never run at the same time, and todo 29 starts only after todo 6 has landed. Todos that add message keys regenerate `keys.rs` after rebasing.
