# kcc-review-remediation - Work Plan

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**Who this is for and what changes for them:** You and anyone you let manage your routers, through the web page, the command line or an AI assistant. Today the same risky change can be protected differently, reported differently and audited differently depending on where you made it, and a few safety and config features do not work as documented; after this work they behave the same everywhere and as written, and the code is smaller and easier to keep correct.

**What you'll get:**
- One safety step that every part of kcc uses when a change could cut it off from a router, so a router is never left counting down to a rollback or reboot without you being told.
- Working lockout, router-name and router-login settings.
- Operators who can apply presets and migrations.
- An audit log that never loses an entry because another kcc process was busy.
- Every router password, login token and read-only login kcc keeps is encrypted and can be set from the web page (and the command line); kcc refuses secret files other users could read.
- A noticeably smaller web interface codebase with one way of doing each thing.
- Leaner tests, no dead code, and a plain-language list of what is still open.

**Why this approach:** Most of the bugs found in the review come from the same safety logic being copied into four places and drifting apart, so the plan fixes the dangerous cases first with tests that prove them, then moves that logic into one shared place before any cleanup. The web interface cleanup is checked page by page against a snapshot of today's pages, so nothing you see changes by accident.

**What it will NOT do:**
- It will not add new libraries, new settings or new features beyond the decisions below.
- It will not change the format of existing stored data or of the audit log; it only adds new encrypted credential records.
- It will not touch your real router: hardware tests stay off until you run them.

**Effort:** XL
**Risk:** Medium - wide refactors of safety-critical and web code; each step is guarded by tests written first and by page snapshots, and the end checks stop after a fixed number of rounds.
**Decisions to sanity-check:**
- Operators may apply migrations and presets and make management changes. The recovery timer around a change runs under that change's own permission; rollback, reboot-type steps and manual timer control still need the Destructive permission.
- Which safety net is used: routers in router mode get the fail-safe timer; access points, extenders and repeaters get a scheduled reboot. When a router does not say its mode (4.3 and 5.0), the fail-safe timer is used if the router shows one, otherwise the change is refused. An unknown reported mode is refused. Unreported-mode behavior is documentation-based, not tested on hardware.
- Router `auth` and `token_file` settings become real for routers listed in the config file.
- When the audit log is locked by another kcc process, entries wait in order and are written later; you are told "entry pending" instead of a false router error.
- Router credentials: the web page and the command line can set the password, a login token and a read-only login, all stored encrypted; a password file given to the command line is read once and sealed, so you can delete it; routers declared in the config file still read their files, and every secret file must be private to kcc's user.
- The unused session keepalive, the unused secret-reveal component and 39 unused texts are deleted rather than finished.
