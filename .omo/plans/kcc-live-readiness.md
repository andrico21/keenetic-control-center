# kcc-live-readiness - Work Plan

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**Who this is for and what changes for them:** You, running kcc in Podman against your Keenetic Ultra on firmware 5.1.10. Today most pages fail and the logs don't say why; afterwards every page shows your router's data, the DNS and VPN server changes work, and each failure leaves one clear log line that never contains secrets or personal data.

**What you'll get:**
- Logs that name the cause of every failed router request (refused, reset, timed out, TLS, HTTP status, router error, or the exact field kcc could not read), with optional debug logs of every request.
- Pages and the CLI that tell those cases apart instead of saying "did not answer".
- Fixes for every page that failed on your router, built from a read-only capture of its real answers, plus the Diagnostics tools, the dashboard's client count and new-device alerts, which fail the same way.
- A test simulator that now answers like real hardware.
- A confirm-password field, router names with spaces or in Cyrillic, a Segments explanation, updated docs.
- Release 1.0.1, published by the agent once you agree.

**Why this approach:** Research on your router (read-only) found the root cause: kcc's decoders and its simulator were written from documentation and never met real hardware. 17 reads have a different shape, long-running commands (ping, the log stream, the component list) continue in a different way, the router ignores kcc's paging of active connections, and one VPN request makes the router answer HTTP 500. Fixing them against your router's real answers, while keeping your data out of the repository, is the only way to be sure. The logging work makes the next unknown firmware diagnosable from a single log excerpt.

**What it will NOT do:**
- The agent never changes anything on your router; you retry the two failing changes yourself. The only active commands it sends are a few pings from the router to itself (one or two packets each), to record and check how the Diagnostics page works.
- Nothing from your network is committed. Captures stay on this machine; tests use made-up values with the same structure.
- Existing MCP and CLI JSON outputs only gain fields, and metrics are unchanged.

**Effort:** XL
**Risk:** Medium - the simulator moves to real shapes, which touches many tests; every change lands test-first and is checked on your router read-only.
**Decisions to sanity-check:**
- Captures and your router's address and name never enter git (this repository is public), only synthetic fixtures with the same structure; the agent keeps your router's details in local files that git ignores.
- Decoders keep accepting the old shape where one alias or envelope branch does it (for firmware lines nobody has captured yet).
- The mesh page drops the "online" column the router doesn't report and shows model, mode, IP, firmware, clients and internet instead.
- The "type to confirm" field for destructive actions asks for the router ID, not its new name.
- A router name that has no Latin letters gets an ID like `router-1`, which you can edit when adding the router.
- Once you give a router a name, going back to 1.0.0 needs that name removed first; routers without a name stay compatible.

Your next move: start it with `$ulw-execute kcc-live-readiness` once both reviews have approved it (their result is reported with this plan). You'll be asked twice to retry the DNS and VPN server changes, and once to approve publishing 1.0.1.

## Execution strategy
### Parallel execution waves
> Target 5-8 todos per wave. Fewer than 3 (except the final) means you under-split.

Todo numbers are identifiers; execute by the dependency matrix. Each todo runs in its own worktree from current `master`, lands as one commit, is rebased onto `master`, passes G0 on the rebased tree, fast-forwards `master` and is pushed with `git -c credential.helper='!gh auth git-credential' push origin master` (never forced). At most two cargo builds run at once (4-core host). Todos that add Fluent messages run `cargo xtask i18n-gen` after rebasing. Lessons that already broke CI (keep them): the Windows main thread has a 1 MiB stack (box large async arms; re-measure CLI paths that gain commands), no paused tokio clock with any fake over loopback TCP, no wall-clock or calendar dependence in tests, absolute per-test state directories for child `kcc serve`, `kcc_testkit::toml_text::path` for paths inside TOML, SIGHUP/SIGTERM tests `cfg(unix)`. `<start>` is the `master` commit at which execution begins; the executor records it in `.omo/evidence/kcc-live-readiness-start.sha` before the first todo.
