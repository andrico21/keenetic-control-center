# Draft: kcc-entware-mcp

## Owner decisions (2026-11-20)
- D-MERGE: merge the MCP work into the (not yet executed) kcc-entware plan; one plan, one run.
- D-AUTH: MCP authentication methods: API keys (stay), kcc login via the Web UI (kcc acts as OAuth 2.1 authorization server: browser redirect to the kcc Web login + consent, tokens bound to the kcc account and its role, revocable on the Web UI), external OIDC IdP (Keycloak/Authentik/Entra etc. through rmcp-server-kit's JWT validation and proxy, claims mapped to kcc roles), mTLS client certificates (kit `MtlsConfig`: CA, optional/required, CRL), and optional API key expiry.
- D-PREC: Web-managed MCP settings live in a state file; kcc.toml values are the defaults; a key the operator marks locked in kcc.toml is read-only on the Web.
- D-PORT: MCP may get its own optional listener (port, bind, TLS, on/off) configured on the Web and applied in-process; default stays `/mcp` on the main listener.
- Owner request (2026-11-20): "MCP should be also controllable via web ui (gated with admin permissions): port configuration, auth, API keys."
- Carried from kcc-entware (binding): D-SCOPE, D-SSHLIB, D-BOOTSTRAP, D-SSHPERM, D-OVERLAY, D-LATEST, D-VET, D-DELIVERY, D-NODEPLOY (see .omo/drafts/kcc-entware.md).

## Defaults to announce (reversible; each confirmed against the research below)
- New permission `ManageMcp` (admin only) for the MCP settings, listener and auth pages and for issued-token revocation; API keys stay under `ManageUsers`. Permission::ALL grows to 13.
- Never expose the kit's `AuthConfig.enabled = false`: network MCP without authentication stays impossible; stdio stays the only unauthenticated path, unchanged.
- Safety-reducing changes (allow_destructive on, `raw` toolset on, read_only off, a new auth method or IdP, mTLS required->optional, CIMD on, a non-loopback MCP bind) need the admin's password re-entered and are audited; settings pages never echo a secret.
- Precedence (D-PREC): environment override (`KCC_MCP_*`) > kcc.toml key marked locked > state file (`mcp_settings.json`) > kcc.toml value > built-in default; env-set and locked keys show read-only on the Web with the reason.
- Endpoint placement: `[mcp] endpoint = main | dedicated | both` (default `main`, today's behaviour). The dedicated listener (bind, port, on/off) reuses the main listener's TLS certificate or a kcc-generated self-signed one; no Web-entered file paths (no arbitrary file reads).
- Live apply: API keys and roles via the kit's ReloadHandle (as today); toolsets, read_only, allow_destructive, max_result_bytes through the per-session handler factory reading an ArcSwap'd config plus `reload_rbac` (new sessions see the change; open sessions keep theirs until reconnect); auth methods, TLS and listener changes by a graceful in-process restart of the affected kit server (the dedicated listener alone, or the main server after the response is flushed; Web sessions survive because WebState is reused).
- kcc as OAuth 2.1 authorization server: issuer = the main listener's public origin (where the Web login cookie lives); endpoints RFC 8414 metadata, `/oauth/authorize` (Web login + consent page in kcc's own templates, six locales, CSP frame-ancestors none), `/oauth/token` (authorization_code with PKCE S256 only, refresh_token with rotation), `/oauth/register` (RFC 7591 DCR for public clients, loopback/https redirect URIs only, exact match except loopback port), `/oauth/revoke`, JWKS; RFC 8707 `resource` required and bound to `aud`; RFC 9207 `iss` in responses; access tokens JWT (RFC 9068, EdDSA signed with a sealed Ed25519 key, 15 min), refresh tokens opaque (sealed store, 7 days, rotation with reuse detection revoking the family), authorization codes 60 s single use.
- Token holder authority: `sub` = kcc account; kcc's MCP handlers re-resolve the account and its current role on every call (disabled/deleted account, role change and Web revocation take effect at the next call, not at token expiry), the same way Web sessions follow users.json.
- Validation path: the kit validates kcc-issued JWTs through its normal OAuth path with `jwks_uri` on kcc's own main listener, admitted by an exact `OAuthSsrfAllowlist` entry for the listener address (no custom validator hook exists in the kit); allowed algorithms for kcc's issuer: EdDSA only.
- External OIDC IdP: issuer, audience, JWKS URL, role claim + claim-value->role mappings or scope->role mappings, optional CA bundle; https only; the kit's SSRF guard stays on, private IdPs need an explicit allowlist entry the admin adds; the kit's proxy (`authorization_server` mode) is used so MCP clients see kcc as the authorization server and the IdP behind it, with the kit's own consent page.
- Client registration: DCR and admin pre-registration; Client ID Metadata Documents (CIMD) off by default (fetching client-hosted URLs would be a new outbound destination), switchable on by the admin later with the kit-style SSRF guard.
- mTLS: CA bundle uploaded on the Web (stored in state, not secret); `required` default false on the main listener (browsers keep working) and selectable on the dedicated listener; all mTLS identities get the configured default role (kit behaviour); CRL checks kit defaults (outbound only to the CA's CRL distribution points). Note: almost no MCP desktop client presents client certificates over Streamable HTTP today (research); mTLS serves scripts, custom agents and proxies.
- API key expiry: optional `expires_at` per key (kit ApiKeyEntry.expires_at, verdict Expired), set on Web and CLI (`--expires-in <duration>`), shown in the table, expired keys refused by the kit and flagged on the page.
- Overlay deviation 6 amended: add OIDC IdP endpoints, CRL distribution points and (when enabled) CIMD URLs as admin-configured non-router destinations under the kit's SSRF guard (metadata always refused); Telegram `api_url` stays kcc.toml-only.
- Secrets sealed under the master key, never shown again: token signing key, refresh-token store, OIDC client secret, kit proxy sealing secret.
- kcc-entware content is carried over unchanged; its MCP toolsets `entware` and `entware-ssh` become two more Web-switchable toolsets (still off by default, `entware-ssh` counted as safety-reducing).
