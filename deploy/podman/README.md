# Rootless Podman deployment

kcc ships as a hardened OCI image: a static musl binary on
`gcr.io/distroless/static-debian13` (no shell, no package manager), running as the
image's `nonroot` user (65532), with a read-only root filesystem, no capabilities,
`no-new-privileges`, a traced seccomp **allowlist**, and memory/PID limits. The binary
itself refuses to start as root (exit 77) and clears every capability set at startup.

| File | Purpose |
|---|---|
| `Containerfile` (repository root) | builder `rust:1.100.0-alpine` and runtime `distroless/static-debian13`, both pinned by digest |
| `deploy/podman/kcc.container` | Quadlet unit for `systemctl --user` |
| `deploy/podman/run.sh` | the same flags for a plain `podman run` |
| `deploy/podman/kcc.toml.example` | configuration for the container layout |
| `deploy/podman/seccomp-kcc.json` | generated syscall allowlist |
| `deploy/podman/e2e.sh` | end-to-end drive of every I/O path, natively or against the container |

**Never** run the container as root, add capabilities, use `--privileged`, or disable
seccomp. If something fails under the profile, debug it as described in
[Debugging a denial](#debugging-a-denial) instead.

## Prerequisites (rootless)

1. Podman 4.4 or newer (Quadlet) running as your own user:
   `podman info --format '{{.Host.Security.Rootless}}'` must print `true`.
2. Subordinate ids for your user (the image user 65532 must map into them):
   `grep "^$USER:" /etc/subuid /etc/subgid` shows a range of at least 65536 ids;
   otherwise an administrator runs `usermod --add-subuids 100000-165535 --add-subgids 100000-165535 $USER`.
3. Lingering, so the user service runs without a login session:
   `loginctl enable-linger "$USER"`.
4. Published ports must be >= 1024 (`net.ipv4.ip_unprivileged_port_start` is not
   touched); the unit publishes 8443 and, optionally, 9090.

## Install

```sh
mkdir -p ~/.config/kcc/etc ~/.config/containers/systemd
cp deploy/podman/kcc.toml.example ~/.config/kcc/etc/kcc.toml      # edit routers, public_url
cp deploy/podman/seccomp-kcc.json ~/.config/kcc/seccomp-kcc.json
cp deploy/podman/kcc.container ~/.config/containers/systemd/kcc.container
```

The `[web] public_url` host is the SNI `kcc healthcheck` sends, so the certificate must
carry it. kcc derives its browser Origin allowlist from that URL and the listener;
`[server] allowed_origins` adds any other trusted proxy origins. The unit's `HealthCmd`
uses the exec (JSON) form: the plain-string form becomes `CMD-SHELL`, which needs
`/bin/sh`, and distroless has no shell. The unit's `StopTimeout=100` covers the server shutdown (30 s) plus 10 s reserved for stopping the scheduler, the bracket grace (10 s), job drain (30 s), queued Telegram notifications (2 s), audit flush (5 s) and a 13 s margin; keep it at least this value.

The optional MCP-only listener (`[mcp.dedicated]`, default port 8444) serves `/mcp` only,
without the Web UI and without metrics. To reach it from the host, set `bind = "0.0.0.0"`
(with `public_url` and `tls = "main"` or `"self_signed"`, since plaintext is accepted only
on loopback) and uncomment `#PublishPort=127.0.0.1:8444:8444`; publish beyond the host
loopback only behind its own TLS. `StopTimeout=100` stays sufficient with it: both
listeners drain at the same time within the one `server.shutdown_timeout`.

### Secrets

Everything secret is a Podman secret mounted read-only for uid 65532 with mode 0400;
nothing secret lives in the config directory or in the image. kcc refuses a secret file
(router password, log sink credential, TLS key) that group or others can read, so keep
`mode=0400` (or 0600) on every further `Secret=` line.

```sh
# 32-byte master key that encrypts the state store
head -c 32 /dev/urandom | podman secret create kcc-master-key -
# TLS pair: an existing certificate, or a self-signed one generated by the image itself
mkdir -m 700 /tmp/kcc-tls
podman run --rm --userns=keep-id:uid=65532,gid=65532 --read-only --cap-drop=ALL \
  --security-opt no-new-privileges --security-opt seccomp=deploy/podman/seccomp-kcc.json \
  --network none -v /tmp/kcc-tls:/out:Z \
  ghcr.io/andrico21/keenetic-control-center:latest tls self-signed --host localhost --out-dir /out
podman secret create kcc-tls-cert /tmp/kcc-tls/kcc-cert.pem
podman secret create kcc-tls-key /tmp/kcc-tls/kcc-key.pem
shred -u /tmp/kcc-tls/kcc-key.pem
# one secret per router password, referenced by password_file in kcc.toml
printf '%s' 'router-password' | podman secret create kcc-router-home -
```

Add a `Secret=` line to `kcc.container` (or a name to `KCC_ROUTER_SECRETS` for
`run.sh`) for every further router secret.

### Volumes

- `kcc-state` (named volume) at `/var/lib/kcc`: users, API keys, audit log, backups,
  encrypted presets and plans. `:U` chowns it to the container user on first use, `:Z`
  gives it a private SELinux label.
- `~/.config/kcc/etc` at `/etc/kcc`, read-only (`:ro,Z`): `kcc.toml` only.

### First run

```sh
systemctl --user daemon-reload
# create the first administrator (prints a one-time password) before starting the
# service: a one-shot container with the service's secrets, volume and profile
s() { printf -- '--secret=%s,target=/run/secrets/%s,uid=65532,gid=65532,mode=0400' "$1" "$1"; }
podman run --rm --read-only --cap-drop=ALL --security-opt no-new-privileges \
  --security-opt seccomp="$HOME/.config/kcc/seccomp-kcc.json" \
  "$(s kcc-master-key)" "$(s kcc-tls-cert)" "$(s kcc-tls-key)" "$(s kcc-router-home)" \
  -v kcc-state:/var/lib/kcc:U,Z -v ~/.config/kcc/etc:/etc/kcc:ro,Z \
  ghcr.io/andrico21/keenetic-control-center:latest --config /etc/kcc/kcc.toml admin init
systemctl --user start kcc
podman healthcheck run kcc && podman inspect --format '{{.State.Health.Status}}' kcc
```

Further CLI commands run inside the service container under the same profile:
`podman exec kcc /kcc --config /etc/kcc/kcc.toml <command>`.

Without Quadlet, `deploy/podman/run.sh [image]` starts the same container.

### Metrics stay on host loopback

Inside the container the metrics listener must bind `0.0.0.0:9090` with
`allow_non_loopback = true`: Podman forwards a published port to the container's
interface, not to its loopback. Exposure is decided by the publish address, so publish
it on host loopback only (`PublishPort=127.0.0.1:9090:9090`, `KCC_PUBLISH_METRICS=1` for
`run.sh`) and let a local Prometheus or a TLS-terminating proxy scrape it. The Web UI is
published the same way (`127.0.0.1:8443`); put a reverse proxy in front of it for
remote access.

## The seccomp profile

`seccomp-kcc.json` is an allowlist: `defaultAction` is `SCMP_ACT_ERRNO` with
`defaultErrnoRet` 1 (`EPERM`), so anything not listed fails with an error kcc can report
rather than killing the process. `clone` is allowed only without namespace flags;
`clone3` answers `ENOSYS` (38) because seccomp cannot inspect its flags, and `ENOSYS`
makes any caller fall back to `clone` (the static musl binary never calls `clone3`).
The profile names only `x86_64` and `aarch64`, the two architectures the image is built
for; the kernel refuses a syscall made through any other ABI (32-bit `x86`, `x32`, `arm`)
as if no rule allowed it.

### How it was derived

By tracing, not by reasoning. The profile is generated and must not be edited by hand.
One trace can miss a syscall a timing-dependent path makes only sometimes, and each
architecture makes syscalls the other's trace never shows, so the profile is generated
from the union of four traces: two per architecture. The `Build and e2e` jobs of
`.github/workflows/container.yml` take them natively on an amd64 and an arm64 runner
(the static binary that ships, run under `strace -f -qq -ff` while e2e.sh drives every
I/O path) and upload them as the artifacts `seccomp-trace-amd64` and
`seccomp-trace-arm64` (directories `seccomp-trace` and `seccomp-trace-2`, kept 14 days):

```sh
T="${CARGO_TARGET_DIR:-target}"
# 1. download both architectures' traces of one container run
rm -rf "$T/seccomp-ci" && gh run download <run-id> -n seccomp-trace-amd64 -n seccomp-trace-arm64 -D "$T/seccomp-ci"
# 2. union all four traces; `gen` reads every file whose name starts with `trace`, so
#    the suffixes keep the sets apart
rm -rf "$T/seccomp-trace-union" && mkdir "$T/seccomp-trace-union"
for arch in amd64 arm64; do
  for n in "" -2; do
    for f in "$T/seccomp-ci/seccomp-trace-$arch/seccomp-trace$n"/trace*; do
      cp "$f" "$T/seccomp-trace-union/$(basename "$f").$arch$n"
    done
  done
done
# 3. review what changes (exits 1 when the profile differs), then write the profile
cargo xtask seccomp gen --check --traces "$T/seccomp-trace-union"
cargo xtask seccomp gen --traces "$T/seccomp-trace-union"
```

Name every added and removed syscall from step 3 in the commit message, then prove the
new profile with the container run under [Verification](#verification).

A local trace covers only the host's architecture, so use it for debugging, not to
regenerate the profile:

```sh
T="${CARGO_TARGET_DIR:-target}"
podman build --format docker -t kcc:test .
podman create --name kcc-extract kcc:test && podman cp kcc-extract:/kcc "$T/kcc-musl" && podman rm kcc-extract
cargo xtask seccomp trace --binary "$T/kcc-musl"                              # -> $T/seccomp-trace
```

`cargo xtask seccomp gen --check-missing` is the drift check CI runs after the two fresh
traces on both architectures (`container.yml`, against the union of the job's own two
traces): it fails only when a traced syscall is missing from the committed profile.
Names only the profile allows pass, because they vary between traces.

`deploy/podman/e2e.sh --native <kcc> [--trace-dir <dir>]` or `--container [--image <ref>]
[--seccomp <profile.json>]` runs named steps. Each step runs with `set -e`, so a command
that fails in the middle of a step fails it: the script prints `FAIL <step>` and its log and
exits 1 at the first failure, or after every step with `--keep-going`. kcc refuses a
password file others can read, so the script writes the web user's password file and the
fake bot token file with mode 0600 and, in container mode, delivers them as Podman secrets. It drives: startup including
the privilege floor and the root refusal, the TLS handshake, Web login, the dashboard SSE stream, a domain read, write
and save against a fake router, a migration plan/apply/commit between two fake
routers, a backup download, the `/metrics` scrape, log forwarding to fake Loki and fake
Elasticsearch, a Telegram test message (`kcc notify test`) to a fake Bot API, a backup
schedule created on the Web admin page and started with "run now" (its backup and its
Telegram message), MCP over HTTP (`tools/list` and one call), `kcc healthcheck`, router URLs
that need name resolution (`/etc/hosts` and a real resolver query), the outbound
connection to the router, a `SIGHUP` configuration reload, and a graceful `SIGTERM`.
The fakes run on the host from the `kcc-testkit` binaries (`kcc-fake-router`,
`kcc-fake-sinks`); the container reaches them through pasta port forwards on its own
loopback.

The first fake router also serves the fake Entware SSH server (`--entware-ssh-port`,
`KCC_E2E_SSH_PORT`, default 18422, forwarded into the container like the router ports).
The `entware-ssh` step runs `kcc entware ssh enable` and `probe`, a `bootstrap` with a
wrong root password (refused, exit 3), a second probe and the `bootstrap` with the
password file (a Podman secret in container mode), `packages list`, `packages install
mc`, `services restart S80nginx` and `ssh revoke`, after which `packages list` is refused
(exit 10). So the SSH client, its key handling and the enrolment run inside the container
under the profile.

The configuration also enables the dedicated MCP listener (`[mcp] endpoint = "both"`,
`[mcp.dedicated]` on `KCC_E2E_MCP_PORT`, default 18444, `tls = "self_signed"`,
`public_url = "https://localhost:<port>"`; in the container it binds `0.0.0.0` and is
published on `127.0.0.1:<port>`, like the Web UI). Four MCP steps follow:

- `mcp-dedicated`: downloads the listener's certificate from the MCP page; an unknown
  API key is refused (401) and `tools/list` with the API key succeeds there.
- `mcp-mtls`: an `openssl`-generated client CA and client certificate; the CA is uploaded
  on the MCP page and `auth.dedicated.mtls = "required"` saved there (with the password
  re-entry, then the restart is polled until applied); `initialize` without a certificate
  is refused and `tools/list` with it succeeds.
- `mcp-main-restart`: saves `auth.main.oauth = "kcc"` on the MCP page with CSRF and the
  password re-entry, polls the status fragment until the restart of the main listener is
  applied (bounded by its deadline, `server.shutdown_timeout` + 10 s), then `/healthz`,
  the dashboard with the session from before the restart, and `/metrics` answer.
- `mcp-oauth`: the whole "Sign in with kcc" flow with `curl` and `openssl` on the main
  listener (issuer `https://localhost:<web port>`): protected-resource and
  authorization-server metadata, registration with a loopback redirect URI, the
  authorization request, the Web login carrying the request id, the consent approval
  (CSRF header, `code` read from `HX-Redirect`), the token request with the S256
  verifier and `tools/list` with the access token, so the kit's loopback JWKS fetch runs
  inside the container; then `kcc mcp connections revoke` and the next `tools/list` of
  the same session is refused (`forbidden`).

`--only <step>[,<step>...]` runs the start-up steps (`privilege-floor`, `accounts`,
`startup`, `healthz`), the named steps and the closing `graceful-sigterm` and `no-denials`
(`mcp-oauth` brings `mcp-main-restart`, which switches the main listener to kcc
sign-in), for example `bash deploy/podman/e2e.sh --container --only entware-ssh`.

The generator assigns every traced syscall to a fixed rationale group
(`xtask/src/seccomp_groups.rs`) and fails on a syscall no group lists, so a new kind of
I/O cannot slip in unreviewed. It also adds:

- the **container-runtime exec prologue** (`close_range`, `capget`/`capset`, `prctl`,
  `execve`, ...), which crun/runc call after installing the filter and which a native
  trace cannot see;
- the **aarch64 equivalents** of traced legacy x86_64 syscalls (`open` -> `openat`,
  `poll` -> `ppoll`, `epoll_wait` -> `epoll_pwait`, ...): a fixed table
  (`EQUIVALENTS` in `xtask/src/seccomp_groups.rs`) allows, for every legacy name a trace
  contains, its generic replacement, which aarch64 has instead. It does not replace the
  arm64 traces: an aarch64 syscall with no x86_64 legacy counterpart comes only from
  them.

`getsockopt` is the lesson behind "drive every path": a non-blocking `connect` is
completed by `getsockopt(SO_ERROR)`. A profile without it lets the container start,
listen and pass `/healthz`, and then fails every router request.

### Verification

Build, then run the e2e drive against the container under the profile:

```sh
podman build --format docker -t kcc:test .
bash deploy/podman/e2e.sh --container --image kcc:test
```

The container runs with
`--read-only --cap-drop=ALL --security-opt no-new-privileges --security-opt seccomp=deploy/podman/seccomp-kcc.json --memory=256m --memory-swap=256m --pids-limit=128`;
every step must pass, `podman inspect --format '{{.State.Health.Status}}'` must report
`healthy`, the metrics scrape passes `promtool check metrics`, `podman run --user 0
kcc:test --version` exits 77, and the container log must contain no
`Operation not permitted`, `EPERM` or `ENOSYS`. The log check alone is not enough: kcc
reports a refused `getsockopt` as "RCI transport failed", so the functional steps
(router reads, migration, metrics `keenetic_up 1`, log forwarding) are what prove the
outbound path. A copy of the profile without `getsockopt` keeps startup and `/healthz`
green and fails exactly those steps.

### Debugging a denial

A missing syscall shows up as an `Operation not permitted` (os error 1) in
`podman logs kcc` or as a failing feature. To find it without guessing:

1. Copy the profile and set `"defaultAction": "SCMP_ACT_LOG"`: the kernel then logs every
   syscall it would have refused (to the audit log / `journalctl -k`, `type=SECCOMP`)
   instead of failing it. Use it on a test instance only, and never ship it.
2. Or reproduce natively: `cargo xtask seccomp trace` and `cargo xtask seccomp gen
   --check-missing` print the traced names the profile lacks.
3. Assign the new syscall a group in `xtask/src/seccomp_groups.rs`, regenerate, review
   the diff, and rerun the container e2e.

`SCMP_ACT_ERRNO` is deliberate in preference to `SCMP_ACT_KILL_PROCESS`: a missed
syscall becomes a reportable error, not an instant kill without a diagnosis.

## Image signing

Release images are pushed to `ghcr.io/andrico21/keenetic-control-center` by
`.github/workflows/container.yml` on release tags (`1.2.3`, no `v` prefix), after every CI
gate passes. A prerelease tag (one with a `-`, such as `1.1.0-rc.1`) is published only
under its own tag and does not move `:latest`, so a unit or `run.sh` on `:latest` stays on
the last stable release.
The image's `org.opencontainers.image.version` label carries the tag's version. They are not signed yet; until they are,
pin the image by digest (`Image=ghcr.io/...@sha256:...`) after verifying it, or build
it yourself from a tagged checkout. When signing is added (`cosign sign --yes` with the
workflow's OIDC identity), verify with `cosign verify` and enforce it with a
`policy.json` `sigstoreSigned` requirement for the repository.
